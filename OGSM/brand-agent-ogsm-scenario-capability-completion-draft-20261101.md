# 品牌 Agent OGSM 业务场景与能力图谱补全

## 0. 先说结论

你这两栏写不出来，不是因为不懂跨境电商，是因为**这两栏在你的表里被填成了别的东西**：

| 你的栏目 | 实际填的内容 | 举例 | 应该填的内容 |
|---|---|---|---|
| 业务场景 | 功能流水线 | 「配置与问句库 → 采集探针 → 解析与指标 → 诊断洞察」 | 谁、什么触发、面对什么经营问题、做哪些业务动作、产出什么、怎么验收 |
| 能力图谱 | 进度状态 | 「已完成 / 进行中 / 方案中」 | Agent 具备哪些可复用的能力原子，没有它业务会怎么失败 |

这两栏都在回答「我的产品做到哪一步了」，而 OGSM 要求的是「我解决谁的什么经营问题、需要什么可复用的本事」。这是**栏位语义错位**，不是内容缺失。

三个直接后果：

1. **无法判断职责边界。** Emily 和 Clone 都写了「脚本」，但两栏都没写谁做哪一层，于是必然打架。
2. **无法判断能力复用率。** 6 个产线在等 Source 采集，但没有任何一栏记录「采集」是共享能力还是各造一遍。实际是各造了 5 遍。
3. **无法判断「已完成」意味着什么。**「内容审计规则引擎 已完成」——是功能上线了，还是业务结果变好了？现在无法区分。

另外两个硬缺口：`Clone` 和 `Market` 在附件里除名字外完全空白；整份 OGSM 在**交易侧**（转化优化、履约、库存、客服工单、复购订阅、定价促销）零覆盖，14 条产线里只有 Shopify 一条碰到钱。

本文按四层交付：全链路地图 → 14 条产线逐条补全 → 共享能力底座 → 结构性批判与回填方法。

## 1. 全链路业务场景地图

### 1.1 十一段链路与经营主指标

```text
S1 品类机会 → S2 产品/合规 → S3 内容素材 ─┬→ S4 达人/媒体/联盟 ─┐
                                          └→ S5 付费投放 ──────┴→ S6 转化承接 → S7 履约售后 → S8 复购/LTV → S9 品牌资产
S10 数据与决策基建、S11 组织与治理：横切全链
```

| # | 链路段 | 经营主指标（行业真实口径） | 当前挂载 | 典型失效模式 |
|---|---|---|---|---|
| S1 | 品类机会与选品 | 品类搜索增速、CR5、新品 90d 动销率、试单毛利率、退货率 | Market（无流水线）、Shopify（AI 选品）、Echo（产品机会） | 拿平台热搜当需求；不看退货率与合规成本；选品结论无字段，下游接不住 |
| S2 | 产品定义与合规准入 | 认证齐套率、claim 可证率、上架通过率、首次拒审率 | 守衡（只管内容）、Daisy（事实库） | claim 无证据；类目认证/进口合规缺失；上架后被迫改文案 |
| S3 | 内容与素材供给 | 周素材产出、CTR、2s/6s 播放率、素材半衰期、单条成本 | Emily、Clone、守衡、GEO、Daisy | 产能不足；抄皮不复刻机制；素材无谱系；音乐/肖像授权踩线 |
| S4 | 达人/媒体/联盟（earned） | buyer guide 收录数、回复率、CPA、新客数、品牌词搜索 lift | Vicky、Radar、Emily（brief）、GEO（分发） | 名单过期；paid 当 editorial；寄样无回收；授权无台账 |
| S5 | 付费投放 | MER（总营收/总营销费）、ROAS（平台口径仅用于优化）、CAC、CPM、CVR、频次、iROAS | **无** | 素材断档；预算平均分；学习期反复重置；归因窗口混用 |
| S6 | 转化承接（站/店铺） | CVR、AOV、加购率、checkout 完成率、Listing/A+ 质量分 | Shopify（仅独立站） | PDP 与广告承诺不一致；无 CRO 实验；Amazon/TikTok Shop 站内无人 |
| S7 | 履约与售后 | 妥投时效、退货率、CSAT、工单解决时长、差评率 | Echo（仅感知） | 退货原因不回流产品/内容；客服与 VOC 两套系统 |
| S8 | 复购与 LTV | 90/180d 复购率、LTV/CAC、CAC payback、订阅留存、RFM 迁移、贡献毛利 | **无** | 只拉新；邮件/SMS 空转；会员无权益；LTV 用营收口径自欺 |
| S9 | 品牌资产（搜索/心智/AI） | 自然搜索占比、品牌搜索占比、SOV、品牌词 CPC、AI 提及率/准确率、NPS | Signal、GEO、Vicky、Echo | 三套声量口径；mention 次数当 KPI；品牌事实三源不一致 |
| S10 | 数据与决策基建（横切） | 归因覆盖率、指标口径一致率、实验数/月、数据延迟 | Source、Daisy、Main、Echo、Signal、PMO | 四套采集；ID 不统一；报表各算各的；静默失败 |
| S11 | 组织与治理（横切） | 人均 GMV、SOP 覆盖率、审批周期、任务准时率 | PMO、Main、守衡 | 告警三套；责任真空；审批瓶颈；SLA 无 owner |

### 1.2 指标口径（防止用假指标验收）

- **ROAS 分两层**：平台归因 ROAS 只用于投放优化；经营结论用 MER 与贡献毛利 ROAS，避免把平台重复归因当增量。
- **CAC 用 fully-loaded**：（广告 + 工具 + 达人 + 人力）/ 新客数，按平台、品类、首单 cohort 拆。
- **LTV 用 12 个月贡献毛利**，不用营收；看 CAC payback（≤90/180 天），不只看 LTV/CAC=3。
- **复购率按首单 cohort 的 90/180 天同品类复购**，不用全店复购掩盖品类差异。
- **自然搜索占比** = organic sessions / total sessions；**品牌搜索占比** = 品牌词搜索量 / 品类总搜索量，区分 organic brand 与 paid brand。
- **SOV** = 品类内品牌声量份额，按来源加权（媒体/社媒/AI 提及分开），不把 mention 次数直接相加。

### 1.3 三个结构判断

- **0 条产线持有 ROAS / CAC / LTV / 复购率。** 唯一触达交易指标的 Shopify 只有 CVR/AOV，且没定义 CVR 目标。
- **两段完全无产线**：S5 付费投放、S8 复购/LTV。
- **三段只有感知或半个 owner**：S2 产品合规、S6 平台站内、S7 履约售后。

### G1｜加速品牌多渠道声量增长

---

#### 2.1 Emily｜社媒 Agent & 工作台（social.luteos.com）

**定位**：内容链路的「上游决策位」。夹在「产品与 offer 已定」和「素材生产与投放」之间。回答「说什么、对谁讲、凭什么算有效」，不回答「怎么拍出来、出价多少」。

**核心问题清单**

| # | 业务问题 | 谁被折磨 | 触发时点 | 不用的现状 | 不解决的代价 |
|---|---|---|---|---|---|
| 1 | 趋势发现到开拍要 3 周，趋势窗口只有 2-4 周，选题会开完红利已过 | 社媒运营、内容策划、编导 | 每周一选题会；竞品某条 3 天破 50 万播放，老板群里转链接问「能不能跟」 | 人工刷 3 平台 200-300 条视频，截图存飞书表格，会上凭印象挑 5 个；写完到排期再 7-10 天 | 一年跟 40 个趋势，吃到红利不到 5 个；3 人内容团队月成本 6-9 万，大头是过期内容；被迫买流量补曝光，CAC 上浮 20-30% |
| 2 | 只抄爆款的皮，不知道爆的是钩子、objection 回答还是 offer，复刻 10 条中 1 条 | 内容策划、编导、投放 | 竞品或达人某条在类目跑出高播放高转化，决定「复刻一版」 | 复刻同款产品+同款 BGM+同款运镜 | 单条素材成本 800-2000 元，10 条废 9 条，一季度烧 7-15 万，且不沉淀任何结论 |
| 3 | 脚本与 claim 约束脱节，素材拍完才发现不能用 | 编导、品牌市场、合规 | 美妆写功效、母婴被理解为面向儿童、户外写防护数据但拿不出证据；或平台拒审 | 编导按「好看有网感」写，不知 cosmetic claim 不能写成 medical claim | 素材周期从 7 天拖到 20 天，错过整个 campaign 窗口；反复拒审累积账户素材质量信号，影响起量 |
| 4 | organic 与 paid 吃同一套内容，两边都不达标 | 社媒负责人、投放、品牌市场 | 月初排内容日历；投放说「没素材」，社媒说「品牌号掉播放」 | 品牌号发品牌片（播放 3-5 万、转化接近 0），投放用达人混剪（能出单但不敢挂品牌号） | 自然:付费健康比约 7:3，实际做成 3:7，等于用付费预算补自然内容的失败 |
| 5 | 脚本不带判定假设，素材跑不动时无法归因 | 内容策划、投放、品牌负责人 | 一批素材跑两周没起量，复盘三方各说一套 | 脚本只写台词分镜，不写验证什么、目标人群、达标阈值 | 每轮测试烧 1-2 万，产出 0 条可复用结论；一年 12 轮，同一笔钱花 12 次买同一个「不知道」 |

**业务场景链路**

**场景 1｜抢趋势窗口：7 天内把一个上升结构变成 5 条可拍脚本**（周 / 社媒运营+内容策划）
1. 从 Source 拉近 30 天 TikTok/IG/Shorts 该类目 Top100 视频与上升音源，不自建采集
2. 剔除不可用样本：儿童出镜、他牌 logo/水印、平台禁用 claim、宗教与地域禁忌
3. 按「钩子类型 × 人群痛点 × offer 形态」聚类，标出播放增速与发布密度同时上升的 5 个结构，同时标出「总播放高但增速转负」的尸体趋势
4. 对照品牌 claim 库与 Echo 的 objection 榜，判断哪 2 个值得跟、哪 3 个是品类噪音，写明淘汰理由
5. 为 2 个结构各写 2-3 条脚本：前 3 秒画面+台词、卖点、证明方式、CTA、funnel 层、单条测试预算与达标阈值
6. 交编导排期、交达人 BD 做 brief、六项假设登记进测试表、通知 Clone 预留产能

> **验收**：7 天内产出 ≥5 条脚本；≥3 条通过 claim 预检并进入拍摄或达人 brief；其中 ≥1 条 14 天内进入素材测试且 CTR 达品类基线（TikTok 通常 1.5-2%）。
> **失败方式**：只看总播放不看增速，追到已过峰的梗；脚本与当前 offer 对不上，拍完没人投。

**场景 2｜objection 回流：把评论区真问题变成下一轮钩子**（双周）
1. 拉自有账号、竞品账号、达人合作视频的评论与 DM
2. 归到 objection 类型：尺码/合身、成分与安全、效果与时长、物流与关税、价格、使用门槛
3. 筛出「高频 + 现有素材和 FAQ 都没正面回答」的 3 个，排掉品牌根本答不了的
4. 与商品/客服确认标准答案与证据材料（没证据的 objection 不做脚本）
5. 写成反驳型钩子脚本：前 3 秒直接把问题说出来，中段给证据，结尾给动作
6. 同步给 Clone 做变体、给 Echo 校准口径、给 PDP/FAQ 提修改建议

> **验收**：每轮 ≥3 个 objection 有脚本覆盖；下一轮同类 objection 占比下降 ≥20%；≥1 条反驳型脚本进测试且 3 秒留存高于账号均值。

**场景 3｜月度内容配比：定下月 organic/paid、UGC/品牌素材、三平台分工**（月）
1. 盘上月素材表现：按钩子类型、funnel 层、平台统计 CTR/CVR/CPA 与自然互动
2. 定下月目标结构：涨粉 / 搜索沉淀 / 转化 / PR 背书各占多少条
3. 定 UGC 与品牌素材配比（起点参照行业「达人素材贡献 55% 种草素材」，品牌自产:达人原生约 1:3，按月用本品牌数据校准）
4. 定三平台分工：TikTok 承担趋势与转化、IG 承担品牌与复购人群、Shorts 承担搜索意图与产品讲解
5. 给每条内容打三标：目标、首发渠道、是否需要 whitelisting / Spark Ads 授权
6. 输出内容日历与素材需求单，交编导、达人 BD、Clone 排产

> **验收**：100% 内容有目标标记与首发渠道；月末能产出「哪类钩子在哪个平台有效」的结论，且与上月假设逐条可比（验证/推翻/待定）。

**场景 4｜一稿三平台：母脚本改写成 TikTok / Reels / Shorts 三版**（事件驱动）
- 定母脚本：唯一钩子 + 核心 claim + 证明方式 + CTA，先锁定不可变部分
- TikTok 版：3 秒内出冲突、原生口播、上升音源、时长 21-34 秒、字幕避开右侧与底部 UI 安全区
- Reels 版：首帧当封面（网格里必须被看懂）、前 1.5 秒画面钩子、caption 承担主要说明（大量静音观看）、hashtag 3-5 个分层
- Shorts 版：标题写搜索意图关键词、前 2 秒给结论、描述挂链接并做 product tagging、付费合作必须打 paid promotion 标

> **验收**：三版都过平台规格与时长预检；同一母脚本在三平台的 3 秒留存差异能给出归因结论（钩子/封面/标题哪个起作用）。

**场景 5｜测试假设登记：让每条素材失败后能归因**（周）
- 每条脚本立项时写死六项：验证什么、目标人群与 funnel 层、单条测试预算、判定阈值、淘汰规则、对应 objection
- 同步给 Clone（决定出几条变体、改哪个替换位）与投放（决定投哪个受众包）
- 测试跑满后按预设阈值三分：可放量 / 待定 / 淘汰，结论回写脚本库
- 每月汇总「哪类假设被验证、哪类被推翻」，作为下月配比与趋势判断的输入

> **验收**：100% 进入测试的素材有假设记录；每批测试能给出 ≤3 条可复用结论；连续两批可比较，且至少一条被写进下月策略。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 归一化多平台趋势信号 | 只能靠人刷 For You，发现时已过峰；三平台无法横比，选题会只能凭印象投票 |
| 感知 | 监听品牌与竞品内容互动 | 评论区是唯一免费的真实 objection 语料，不看它脚本只能靠猜 |
| 理解 | 归类钩子与卖点叙事结构 | 不知爆在哪一层，复刻只能抄皮，成功率低于 10% |
| 理解 | 归类评论 objection 与未覆盖缺口 | 团队永远在回答已被回答过的问题，真挡住转化的那个没人碰 |
| 理解 | 匹配 claim 约束与内容表达 | 素材拍完才被拒审，返工吃掉 campaign 窗口；不同编导写出不同口径 |
| 推理决策 | 判断趋势可跟性 | 跟错一次成本是两周拍摄产能 + 错过同期一个真机会 |
| 推理决策 | 决定内容配比与平台分工 | 每条内容都想兼顾涨粉和转化，两边都不达标 |
| 推理决策 | 生成测试假设与判定口径 | 素材失败后只能说「素材不行」，无法区分钩子/卖点/offer/投放 |
| 生成 | 生成脚本与分镜 | Clone 和编导拿到的只是「讲一下这个产品」，各拍各的 |
| 生成 | 生成平台化文案 | Shorts 吃不到搜索流量，Reels 承接不了静音观看，TikTok 挂不上话题 |
| 生成 | 生成达人/拍摄 brief | brief 只写「讲真实体验」，回来的素材一定不可用；授权不前置就投不了 paid |
| 执行 | 排期与派发 | 趋势窗口在等待中消耗，没人知道内容卡在谁手里——这是「7 天变 20 天」的直接原因 |
| 评估 | 复盘钩子命中率 | 每年 12 轮测试学不到东西，内容能力不随时间增长 |
| 记忆 | 沉淀品牌内容资产（钩子库/claim 与证据库/品牌调性/失败结构） | 每次从零开始，不同编导写出互相矛盾的口径，被用户和平台同时发现 |

**边界**

- **不自建采集**（Source 的活，只消费其采集结果做趋势口径归一化）；不做舆情预警与风险分级（Vicky/Echo/Signal）；不做达人筛选、报价与外联（Radar/达人 BD）；不成片、不做素材变体与出片规格（Clone）；不碰投放账户、出价与预算；不做最终合规判定——守衡是终审，Emily 只做脚本阶段的 claim 预检。
- **与 Clone 的切分线（最关键）**：「脚本」必须拆成三层，不能两个产品都叫「脚本生成」：
  - ① 原始脚本（Emily）——叙事层，含 claim、目标人群、证明方式、判定假设
  - ② 镜头脚本/分镜（Clone）——执行层，把叙事结构套到真实可用资产（谁能出镜、有没有场景、有没有授权）
  - ③ 变体脚本（Clone）——只换钩子/字幕/CTA/BGM，不改 claim
  - Clone 若要改 claim，必须回 Emily 重走 claim 预检。
- **拒单规则**：Emily 的脚本缺 claim / 目标人群 / 判定假设任一项，Clone 有权不接；Clone 产出的素材缺来源与授权标记，Emily 不纳入内容日历。

> **诚实结论**：Emily 有独立存在必要，因为「趋势→选题→claim 与 objection 对齐」是纯策略判断，Clone 和投放都替不了。但如果 Emily 只做「批量生成脚本」而不做配比决策与假设登记，它就退化成一台文案机，应并入 Daisy 的 skills 平台。

#### 2.2 Clone｜爆款复刻 Agent & 工作台（video.luteos.com）

**定位**：内容链路的「下游产能位」。回答「怎么把已验证结构批量做成能过审、能跑量、可归因的素材」。

> 附件里这条产线除网址外完全空白，以下为从边界反推的补全。

**核心问题清单**

| # | 业务问题 | 谁被折磨 | 触发时点 | 不解决的代价 |
|---|---|---|---|---|
| 1 | 素材产能被人工剪辑卡死，补片速度赶不上素材衰减速度 | 剪辑、内容制片、投放 | 账户素材衰退；新 campaign 要 20-30 条而剪辑手上只有 3 条半成品 | 一条爆款从拆解到成片 3-5 天，一个剪辑一周 5-8 条；TikTok 侧一周至少补 3-7 条，产能缺口 3-5 倍，被迫降测试密度，等于放弃找下一个爆款结构 |
| 2 | 素材疲劳无预警，看到时钱已花完，且分不清是素材衰退还是人群跑窄 | 投放、剪辑 | 单条连续跑 5-7 天；CTR 从 2% 掉到 1% 以下、CPM 从 12 涨到 30 | 每月因「跑不动的素材继续跑」浪费 10-20% 预算；每次关停重开都要重过学习期 |
| 3 | 复刻等于搬运，素材授权踩线 | 剪辑、投放、品牌负责人 | 把达人视频或竞品素材混剪后用 Spark Ads / GMV Max 投流 | 行业流传「混剪不需要授权，投流才需要」，实际可用素材只有店铺授权号、TTAM Spark Ads Video code、ACA、红人联盟授权；一次账号处罚恢复周期以周计 |
| 4 | 素材没有谱系，改 6 版之后无法回答哪个改动让它变好或变坏 | 投放、剪辑、内容策划 | 同一条素材改了 6 个版本要开复盘会 | 报表只到 campaign/ad group 层级，文件命名是「终版-2-改」；同一个错误跨月跨人重复犯 |
| 5 | 多平台规格返工，合规预检靠人眼逐条看 | 剪辑、投放 | 一条 9:16 母版要出三平台版本 | 每版都过一遍人工，出片周期被规格问题拖长 |

**业务场景链路**

**场景 1｜结构复刻：把一条已验证爆款拆成可复用机制再产 15 条变体**（事件驱动）
- 拉原片做逐帧结构拆解：前 3 秒钩子类型、被回答的 objection、证明方式、节奏节点、CTA 位置
- 标出哪一层是「可迁移机制」（钩子逻辑、证明结构），哪一层是「不可迁移皮」（具体场景、具体人物）
- 对照可用资产清单（自有拍摄、达人授权素材、UGC）判断哪层能落地
- 设计变体矩阵：固定 claim 与证明结构，只换钩子/开头画面/CTA/BGM，一轮 15 条
- 出片并打谱系标签：source_structure_id、脚本、变体序号、替换位
- 交付投放并回传结构 ID，供 Emily 写进钩子库

> **验收**：单条爆款结构在 5 个工作日内产出 ≥15 条变体；每条 100% 有谱系标签（可追溯到原结构与脚本）；变体间「只换一个变量」的比例 ≥80%；首轮测试至少 1 条 CTR 达到或被复刻原片基线的 80%。

**场景 2｜素材疲劳预警与替换**（日 / 投放+剪辑）
- 按素材维度（不是账户维度）监控 CTR、CPM、频次、完播、加购
- 判定三分：正常 / 进入衰减 / 已死（CTR<1% 且 CPM>30 且无加购）
- 对衰减素材给出替换建议：同结构新变体、换钩子、还是关停
- 替换素材提前 3 天进入队列，不等断档才补
- 记录每次替换的判定依据，供复盘

> **验收**：任一素材进入衰减后 48 小时内完成替换决策；单账户「跑不动的素材继续跑」浪费控制在 5% 以内；每次替换有判定依据记录。

**场景 3｜授权核验与可投范围判定**（事件驱动 / 每条素材进加热池前）
- 拉素材包、达人合作记录、平台授权凭证（TTAM / Spark Ads Video code / ACA / 红人联盟授权状态）
- 判定四类覆盖范围（不合并成一个「能不能用」）：自然曝光、付费加热、二次剪辑、跨账号复用
- 输出三态：可投 / 部分可投（标明可播片段）/ 不可投（附缺什么凭证）
- 建立素材-授权-账号-有效期四元组台账
- 到期前自动复审，授权撤回时反查所有在用素材

> **验收**：进入加热池的素材 100% 有四元组台账；授权覆盖不足的素材上线数为 0；授权撤回后 2 小时内能列出全部关联在用素材。

**场景 4｜多平台规格化出片**（事件驱动）
- 一条母版出 TikTok / Reels / Shorts 三版：画幅、时长、安全区、封面
- 逐版过规格预检（时长、字幕安全区、封面可读性、product tagging）
- 输出带平台标签的成片包与规格预检记录
- 交投放并按平台分渠道入库

> **验收**：三版一次通过平台规格校验；规格类返工率 <10%；每条成片有平台标签与规格预检记录。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 理解 | 拆解视频结构与可迁移机制 | 复刻只能抄皮，10 条中 1 条 |
| 理解 | 判定素材来源与授权边界 | 混剪绕过授权，把最便宜的免费流量变成侵权与拒审风险 |
| 推理决策 | 判定生产可行性（资产/产能/成本匹配） | 设计出拍不出来的变体矩阵，产能在排队中空转 |
| 推理决策 | 设计变体矩阵（单变量控制） | 改 6 个地方一起改，跑出来无法归因 |
| 生成 | 批量生产素材变体 | 产能缺口 3-5 倍，素材断档导致 CPM 上涨 |
| 生成 | 平台规格化与标注 | 每版人工返工，出片周期被规格问题拖长 |
| 执行 | 素材入库与推送投放 | 素材散在本地与网盘，投放找不到最新版 |
| 执行 | 素材谱系登记 | 复盘无法回答哪个改动让它变好，同一错误跨月重复犯 |
| 评估 | 素材层效果归因 | 分不清素材衰退与人群跑窄，处理方式只能是整组关停重开 |
| 评估 | 素材疲劳预警 | 看到 CTR 下滑时已多跑 3-5 天预算 |
| 记忆 | 素材资产库与失败结构负向清单 | 只存成功案例，不知道什么一定不行，下季度继续试错 |

**边界**

- 不自建采集、不做投放出价与预算执行、不做舆情判定、不做最终合规终审（守衡）、不做达人筛选与报价（Radar）。
- **与 Radar 的切分线**：Clone 复刻的是内容结构与叙事骨架，产出品牌自有素材；一旦要使用达人原始画面、声音或用达人账号发布，必须回到 Radar 的授权台账。**混剪不是规避授权的方法。**
- **与 Emily 的切分线**：Emily 决定「说什么」，Clone 决定「怎么拍成能过审、能跑量、能换皮的片子」。Clone 改 claim 必须回 Emily 重走预检。

> **诚实结论**：Clone 的核心价值不是「生成视频」，而是**产能 + 谱系 + 授权 + 疲劳**四件事。如果只做 AI 生成能力而没有谱系与授权台账，它就是一个更快的侵权工具。

#### 2.3 Vicky｜PR Agent & 工作台（pr.luteos.com）

**定位**：earned media 关系与声誉防守段。核心不是发稿量，而是把媒体/编辑关系变成可复用、可验证、可归因的第三方信任资产。

**PR 的价值链必须写成**：coverage 质量（是否 buyer guide / 榜单 / 高意图栏目）→ 品牌词搜索（滞后 2-8 周）→ 品牌词流量与更高 CVR → assisted conversion 与 NTB。曝光量、AVE、粉丝数不是口径。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 每季度花 15-40 万美金在媒体关系、寄样和 agency，季度汇报只能报「发布 12 篇、曝光 300 万」，CFO 问带来多少新客答不出来 | PR 预算被削 30-50%，团队被迫转做可即时归因的付费投放；品牌信任资产没人建，第二年媒体关系从零开始 |
| 2 | 手上 500 条媒体名单，真正还在写这个类目的活跃编辑不到 50 人；换栏目换人换政策后没人知道，pitch 回复率长期 2-5% | 每季度浪费 200-400 小时筛选；错过上市窗口；单季度 1-3 万美金寄样打水漂 |
| 3 | 把 paid placement 当 editorial 发、把送样当保证收录、把 affiliate publisher 当普通媒体 | 披露缺失导致内容下架、媒体关系断裂、FTC 调查；品牌信任资产一次性归零，恢复周期 12-24 个月 |
| 4 | 媒体负面或 Reddit 高热帖出来 48-72 小时后才知道；知道后所有人转发，没人定级、没人认领、没人回扫 | P0 事件延迟 24 小时响应可能引发二次报道和 10-30% 短期销量下滑 |
| 5 | 同一个 Reddit 差评帖，Echo 报「产品负面」、Signal 报「声量异动」、Vicky 报「舆情预警」，三条告警进三个群，真正的媒体负面反而被淹没 | 告警疲劳导致真事件被忽略；重复建设采集与分类，年化浪费 2-3 人 |

**业务场景链路**

**场景 1｜季度 editorial 攻占**（季度 + 新品上市事件驱动）
1. 定 3 个本季度值得被媒体写的议题，每个写清「读者在问什么 + 品牌能提供的独家证据」
2. 反查过去 90 天写过该议题的媒体与作者，拉出 60 位候选编辑及最近 3 篇文章
3. 按 media fit、编辑 beat、联系可达性、历史互动分 A/B/C，砍到 40 位
4. 逐位判断 route：organic pitch / affiliate-supported / paid partnership / licensing，标清能不能谈钱
5. 为 A/B 级编辑各写 1 页 pitch：为什么是这个栏目、读者在问什么、有什么可验证证据、不干预结论
6. 人工审批后发送或寄样，记录寄样单号与 7/14/30 天跟进节奏
7. 发布后归档 coverage，抽取可复用资产与授权范围，同步到 DTC PDP、Amazon A+、GEO 事实库

> **验收**：90 天内 40 位 fit≥B 编辑全部触达；回复率 ≥8%；≥5 篇 organic 收录，其中 ≥2 篇为 buyer guide/best list；0 起 route 误判（paid 被标 organic）。
> **失败方式**：按媒体流量排序而不是编辑近期选题匹配，用同一封模板群发。

**场景 2｜竞品 editorial 占位监测与补位**（周）
- 每周抓 5 个竞品新增的 editorial 收录、buyer guide 席位、奖项与评测
- 标出「竞品已占、品牌缺席」的栏目与榜单，按读者意图价值排序
- 判断缺席原因：产品证据不足、编辑关系缺失、route 不对、品类叙事不匹配
- 每条缺口给补位动作：补测试数据、换编辑、走 paid/licensing intake，或明确放弃
- 30 天后回看是否补上

> **验收**：竞品集合覆盖率 100%；每个高影响缺口 48 小时内给出补位动作或明确放弃理由。

**场景 3｜舆情事件发现到回扫（分级 → 派单 → 处置 → 48h 回扫）**（日监听 + 事件驱动）
1. 多源监听并去重，合并同一事件的不同转载与讨论
2. 分类：事实错误 / 产品安全 / 服务投诉 / 媒体负面 / 竞品攻击 / 创始人言论
3. 按媒体级别 × 传播速度 × 事实严重性定 P0-P3，写清判定依据
4. P0/P1 在 30 分钟内推给对应处置 owner，开工单，附事实时间线与建议口径
5. 处置 owner 执行动作（客服回复 / 法务声明 / 产品核查 / 媒体沟通），Vicky 记录动作与时间
6. 48 小时回扫：是否被新源转载、AI 回答是否仍引用、原帖是否降温
7. 未闭环升级；闭环后归档为案例，更新口径库与监听词

> **验收**：P0 事件 30 分钟内触达责任人；48 小时回扫执行率 100%；同一类事件季度内重复发生 ≤1 次。
> **失败方式**：只发预警不派单；或把 Echo 的产品 VOC 也塞进 PR 工单，导致告警泛滥。

**场景 4｜商业合作 intake 与披露校验**（事件驱动）
- 收到 media kit、榜单邀约或编辑询价，先判 route：paid / native / affiliate / licensing / organic
- 拉该媒体公开的 editorial policy、sponsorship 标注规则与历史案例
- 校验品牌现有证据能否支撑其栏目要求（测试数据、认证、安全边界）
- 生成 intake 包：目标、预算带、deliverable、披露方式、不可承诺条款（不保证结论、不保证排名）
- 法务与品牌负责人审批后谈判签约
- 发布后校验：披露是否清晰、是否被标为 sponsored、内容是否被错误引用

> **验收**：route 误判 0 起；所有 paid 内容有披露方案且发布后校验通过；0 起「保证正面评价」类条款签署。

**场景 5｜Coverage 资产化与下游联动（PR 价值归因）**（月 + 季度）
- 汇总本月 coverage，逐篇抽取可复用资产：编辑结论、quote、奖项、榜单排名、测试数据
- 标注授权范围：能否用于广告、能否用于 PDP、能否用于 AI 内容、是否需书面许可
- 把授权可用资产分发给下游：DTC 信任模块、Amazon A+、品牌事实库、GEO 引用源
- 建立 coverage → 品牌词搜索 → direct/assisted conversion 的月度对照
- 季度做一次 geo-holdout 或时间序列对照，给出方向性弹性区间并标注不可直接归因

> **验收**：100% coverage 有资产卡与授权矩阵；下游分发记录可追溯；季度报告必须给出「方向性弹性区间 + 不可直接归因标注」，不接受单点数字。
> **失败方式**：把 editorial quote 直接做成广告素材，违反编辑政策；或只归档不联动，PR 永远是成本中心。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 媒体与编辑源监测 | 名单过期不自知，pitch 回复率长期 2-5%，团队误判为「媒体不理我们」 |
| 理解 | 判定媒体/编辑 fit 与 beat | 按流量排序而非选题匹配，同一封模板群发，被编辑拉黑 |
| 理解 | 判定合作 route（paid/native/affiliate/licensing） | 把 paid 当 editorial 发，触发披露违规与 FTC 风险 |
| 理解 | 事件分类与影响面分级 | 三条告警进三个群，真事件被淹没；P0 延迟 24 小时响应 |
| 推理决策 | 事件处置路由与 SLA | 只发预警不派单，责任真空导致事件升级 |
| 推理决策 | 缺口诊断与补位优先级 | 只看竞品发了几篇，不判断栏目意图价值 |
| 生成 | 定制 pitch 包 | 模板群发，回复率 2-5% |
| 生成 | 对外口径与声明草稿 | 对外声明无统一口径，二次报道风险 |
| 执行 | 外联与寄样执行（人工审批门） | 寄样无台账，1-3 万美金单季打水漂 |
| 评估 | coverage 质量与授权矩阵 | editorial quote 被误做成广告素材，违反编辑政策 |
| 评估 | 品牌词 lift 与业务价值归因 | 只能报曝光量，CFO 问新客答不出，预算被砍 30-50% |
| 记忆 | 编辑关系与历史互动记忆 | 每次从零建立关系，媒体关系资产不累积 |

**边界**

- 不做内容生产（Emily/Clone）、不做声量数量与异动（Signal）、不做产品 VOC 语义（Echo）、不做采集（Source）、不做投放、不做合同签署与法务结论（法务签字）。
- **与 Echo 切分**：Vicky 回答「谁在公开说、会不会变成危机」，Echo 回答「说了什么、指向哪个 SKU 与哪句卖点」。
- **与 Signal 切分**：Signal 是前哨与分诊台，Vicky 是处置台，两者共享同一事件单 ID，不重复建单。

> **诚实结论**：PR 线独立成立；舆情线必须并入统一事件服务，否则它与 Echo、Signal 的重叠度约 60%。

#### 2.4 GEO｜专家内容 Agent & 工作台（geo.luteos.com）

**定位**：AI 搜索可见度的测量与攻占。护城河是**测量闭环**（问句库 → 采集探针 → 指标 → 诊断 → 内容 → 复测），不是内容生成本身。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 买家越来越多直接问 AI「哪个牌子好」，品牌在这个场景里完全没有位置，而团队还在看传统 SEO 排名 | AI 推荐位的流量被竞品吃走，且这部分流量意图最强、转化最高 |
| 2 | AI 回答里关于品牌的描述是错的（参数、成分、适用边界），没人知道、没人改 | 错误信息持续影响决策，涉及安全/认证的错误可能引发合规风险 |
| 3 | 只报「提及率 12%」这种孤零零的数字，不排序、不归因、不指定 owner | 团队不知道先做什么，投入分散，季度评审无法判断是否继续投 |
| 4 | AI 引擎频繁更新，上一次的结论下次失效，但没有基线版本与复测协议 | 每次重来，看不到趋势，也无法证明投入有效 |

**业务场景链路**

**场景 1｜建立品牌问句库与多引擎基线**（季度建库 + 月度增量）
- 按品类决策、场景、对比、品牌、疑虑 5 类，生成 300-500 条真实问句
- 每条标注市场、类目、购买阶段、意图价值、对应产品线
- 选定 5 个 AI 引擎与地区，跑同一批问句的基线
- 记录品牌是否被提及、排位、引用源、描述是否准确、推荐了谁
- 基线快照与问句版本入库，指定 owner 与下次复测时间

> **验收**：问句库 ≥300 条且有版本号；基线覆盖 5 引擎 × 目标地区；每条记录含提及/排位/引用源/准确性四项。
> **失败方式**：用关键词工具导出品牌词当问句库；只测 1 个引擎 1 个地区；截完图就结束。

**场景 2｜可见度缺口诊断与主题优先级排序**（月）
- 解析每个回答中的品牌提及、排位、引用源、情感与准确性
- 算五项指标：mention rate、citation share、answer position、accuracy rate、sentiment
- 按「意图商业价值 × 缺口大小 × 可攻占性」排 Top10 主题
- 每个缺口归因到：内容不存在 / 内容不被引用 / 事实冲突 / 引用源被竞品或社区占据
- 为每个主题指定动作与 owner：补内容、修事实、换源、做 PR 收录、社区运营
- 设定 30/60 天复测节点与成功判据

> **验收**：每月产出 Top10 攻占主题，每个有归因、owner、动作与复测判据；不接受只报提及率。
> **失败方式**：只报「提及率 12%」，不排序、不归因、不指定 owner。

**场景 3｜可引用权威内容生产与分发**（月 + 事件驱动）
- 针对每个主题确定「AI 需要什么证据才会引用」：参数、测试、认证、对比、专家观点
- 从事实库取可验证事实，缺的标为待补，**不允许编造**
- 生成结构化内容：FAQ、对比表、方法论、数据页、专家署名文章
- 加结构化标记、来源引用、作者与更新时间，统一实体写法
- 选择分发位：品牌站、PR 媒体、行业目录、Reddit/Quora 等 AI 高频引用源
- 人工审批后发布，记录 URL 与目标问句映射

> **验收**：每条内容 100% 绑定目标问句与事实来源；0 条未证实功效表述通过守衡；发布后有引用监测任务。
> **失败方式**：写成营销软文或 SEO 堆词文，AI 宁可引用 Reddit 和竞品官网。

**场景 4｜AI 错误信息纠正**（事件驱动）
- 监测到 AI 回答含错误参数、过时信息、负面断言或错误归属
- 定位引用源：自有页面、旧媒体文章、第三方评测、Reddit/论坛、竞品内容
- 分级：涉及安全/认证/成分 = P0，参数/适用边界 = P1，评价 = P2
- P0 7 天内修正自有源并补权威出处；同步法务与客服口径
- 对第三方源发起更正：媒体更正请求、商家回复、结构化数据更新、社区澄清
- 30/60 天复测同一问句，确认是否被纠正或不再引用错误源

> **验收**：P0 错误 7 天内自有源修正完成；60 天复测错误率下降 ≥50%；每条工单有引用源清单与更正记录。

**场景 5｜月度复测与业务价值归因**（月 + 季度）
- 用同一批问句、同一引擎、同一地区复测
- 对比五项指标变化，标注模型更新、季节性等外部因素
- 关联下游：品牌词搜索量、direct/non-brand 流量、AI referral、assisted conversion、NTB
- 有条件的市场做 geo-holdout 或时间序列对照，估方向性弹性
- 月报：本月变化、归因、下月 Top10 主题、预算建议
- 季报给 CFO：防守价值（错误率下降、客服工单减少）+ 进攻价值（品牌词搜索、NTB），**明确标注不可直接归因**

> **验收**：月报含五项指标环比 + 外部因素标注；季报必须给区间估计而非单点，且带「不可直接归因」声明。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | AI 引擎回答采集与快照 | 没有基线，所有结论都无法证明有效，也无法复测 |
| 感知 | 引用源与占位归因 | 不知道 AI 为什么推荐别人，攻占动作全是盲打 |
| 理解 | 实体消歧与品牌一致性识别 | 品牌名/型号/成分写法不统一，AI 认不出是同一实体 |
| 理解 | claim 与事实准确性校验 | AI 引用错误参数，涉及安全/认证时变成合规事故 |
| 推理决策 | 缺口诊断与优先级排序 | 只报提及率，团队不知道先做什么 |
| 推理决策 | 可攻占性判断 | 挑到攻不下的主题，投入打水漂 |
| 生成 | 结构化内容生成（可被引用形态） | 写成营销软文，AI 不引用，SEO 堆词无效 |
| 生成 | 诊断报告与月报生成 | 无法向 CFO 交付，投入被质疑 |
| 评估 | 可见度指标与复测 | 单次截图当证据，看不到趋势，无法证明有效 |
| 评估 | 业务价值归因（品牌词 lift / NTB / AI referral） | 只能报提及次数，预算评审通不过 |
| 记忆 | 问句库与基线版本 | 引擎更新后无法对比，每次重来 |

**边界**

- 不做采集器（只允许采 AI 引擎回答这类 Source 覆盖不到的源，其余一律订阅）；不做内容最终合规判定（守衡）；不做舆情处置（Vicky）；不做投放。
- **漏项警告**：当前只覆盖公开 AI 引擎，**漏了 Amazon Rufus 与 TikTok Shop 站内 AI 推荐**——而这两个是品牌真正有交易发生的场景。

> **诚实结论**：GEO 的护城河是测量闭环，内容生成应降级为「按诊断结论产出」，否则它与 Emily 的权威内容生产重复。

#### 2.5 Radar｜IP/名人 Agent & 工作台（magpie.luteos.com）

**定位**：达人/IP 合作的**权属与商业路线** owner。定「找谁、给什么约束、素材能用到哪、这次合作值多少」。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 达人池被当成按粉丝量排序的通讯录，头部名人/中腰部 KOL/尾部 KOC/联盟客没有各自目标和考核，预算摊平后哪层都没跑出效果 | 分层失效，钱花了但没有一层打透 |
| 2 | 合作成本与产出对不上账，说不清是内容有效还是投流有效，续约和加预算只能靠感觉 | 无效达人持续续约，预算被固化在低效池 |
| 3 | 达人内容爆了却因授权没前置而不能投、不能复用，团队用混剪绕过 | 把最便宜的免费流量变成侵权和拒审风险 |
| 4 | 合作风险在签约后才暴露：历史争议、竞品排他、披露缺失、品类 claim 过界 | 任何一项都由品牌兜底，声誉损失不可逆 |
| 5 | 寄样、佣金、退货冲回没有系统台账，钱和货在漏 | ROI 归因从一开始就不可信 |

**业务场景链路**

**场景 1｜为新品首发配置达人金字塔并锁定首轮名单**（事件驱动）
> **验收**：5 个工作日内 ≥40 个候选、覆盖 4 个层级的分层名单，wave-1 ≥12 人；每个候选有可核对的公开合作入口与 route 判定；人工审定通过率 ≥60%；名单里 editorial-only 与 no-sponsorship 对象为 0。

**场景 2｜达人内容爆量后 48 小时内完成授权与付费放大**
> **验收**：识别到首条付费素材上线 ≤48 小时；每条放大素材 100% 有书面授权凭证与到期日；首批测试预算 ≤$1000；授权不全的素材上线数 0。

**场景 3｜月度达人 ROI 结算与续约决策**
> **验收**：本期有合作的达人覆盖率 100%；每人有成本、产出、净 ROI 三个数；与财务对账差异 ≤5%；每条续约建议可追溯到具体口径；止损名单执行前经人工确认。

**场景 4｜签约前达人/名人风险尽调与排他核查**
> **验收**：S/A 级合作 100% 有尽调报告；每条风险结论附可点击证据；红线条款进合同模板；无人工签署的合作数 0。

**场景 5｜周度寄样与佣金台账闭环**
> **验收**：寄样 100% 有单号与签收记录；寄出→发布转化率可按达人统计；佣金异常在一个结算周期内被发现；重复寄样率 <2%。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 监测达人内容与互动异动 | 爆了要等别人告诉你，48 小时窗口错过 |
| 感知 | 监听达人风险与竞品合作信号 | 塌房、竞品排他签约后才暴露 |
| 理解 | 解析达人受众与内容原型 | 按粉丝量而非受众匹配选人，投错人群 |
| 理解 | 判定合作商业路线与门禁 | paid 与 organic 混淆，披露缺失 |
| 理解 | 识别素材可放大性与授权状态 | 爆款因授权不能投，只能混剪绕过 |
| 理解 | 归一化达人成本与产出口径 | ROI 算不出，续约靠感觉 |
| 推理决策 | 配置达人分层与预算配比 | 预算摊平，哪层都没打透 |
| 推理决策 | 排序外联优先级与接触路径 | 逐一试错，回复率低 |
| 推理决策 | 诊断达人 ROI 异常与归因 | 分不清是内容有效还是投流有效 |
| 生成 | 生成约束型 brief 与禁用 claim 边界 | brief 只写「讲真实体验」，素材一定不可用 |
| 生成 | 产出 ROI 结算与续约报告 | 无法向财务交代 |
| 执行 | 发起外联与寄样跟进（人工审批门） | 寄样无台账，货和钱在漏 |
| 执行 | 推进授权申请与素材交接 | 授权滞后于内容爆量，错过放大窗口 |
| 评估 | 评估合作达成率与内容复用率 | 不知道哪层达人在起作用 |
| 协同 | 与 Emily/Clone/投放侧交接权属与 brief | 权属不清，素材用不了/用错 |
| 记忆 | 维护达人/IP 合作资产档案 | 每次从零找人，合作历史不沉淀 |

**边界**

- 不做内容拍摄与脚本成稿（Emily）、不做爆款复刻与素材生成（Clone）、不做品牌级声量与舆情（Signal/Vicky）、不做消费者声音语义（Echo）、不做原始采集（Source）、不做媒体编辑关系与 pitch（Vicky）、不做投放出价与预算、不做合同签署与法务结论（只出尽调材料）。
- **与 Emily 切分**：Radar 定「找谁、什么约束、素材能用到哪、值多少」；Emily 定「内容怎么做、用什么结构」。**达人原始素材的权属与复用许可只在 Radar。**

> **诚实结论**：Radar 只做 IP/名人即可，范围要收窄。达人供应链（寄样/回收/验收/结算/授权回收）是另一件事，当前无人负责，但它未必需要一个独立 Agent——可以先并入 Radar 的一个模块。

#### 2.6 Echo｜VOC Agent & 工作台（radar.luteos.com）

**定位**：回答「说了什么、指向哪个 SKU 与哪句卖点、该怎么改」，服务产品与运营。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 新品上市两周，差评集中在尺码/适配，团队只看到星级从 4.6 掉到 4.2，定位不到是哪个变体、listing 里哪句卖点承诺失准 | 等定位到时已累积 30-40 条一星，新品窗口废掉 |
| 2 | 评论、客服工单、退货原因三套数据各说各话，没人能回答「这个 SPU 到底因为什么被退」 | 整改无靶心，改错地方继续被退 |
| 3 | 同一批用户在 Amazon 评论、TikTok 评论区、独立站、Reddit 说的其实是同一件事，但四个渠道各看各的 | 没有品牌级 objection 榜，内容与 PDP 反复踩同一个坑 |
| 4 | VOC 风险指数被当成展示数字，没和平台商品资格、达人可合作性挂钩 | 指数涨了没人知道下一步会不会掉资格 |
| 5 | 用户说的「想要更小包装 / 更适合敏感肌 / 更透气」散落在评论里，从没被结构化成可立项需求 | 产品迭代靠猜，错过真实需求 |

**业务场景链路**

**场景 1｜定位新品差评根因并回流到 listing 与产品**
> **验收**：T+14 复核，该 SPU 一星/二星中尺码/适配类占比相对 T+3 下降 ≥30%；T+3 识别的每条整改项都有 owner、deadline 与回填证据，挂空率 0；未达阈值时必须写明未解决原因，**不允许只报下降**。

**场景 2｜把评论区 objection 变成 PDP/LP 的承接内容**
> **验收**：前 10 条 objection 中 ≥8 条能在 PDP 上指认到具体承接位置（哪张图/哪句/哪条 FAQ），且 100% 通过守衡预检；上线 14 天该 objection 新增提及率下降 ≥30%，或该页 CVR 相对基线提升 ≥10%，二者至少达成一项并附样本量说明。

**场景 3｜大促与舆情回潮前的 VOC 风险体检**
> **验收**：覆盖 100% 在售 SPU；每个高风险 SPU 必须有「修/不修 + 理由 + 止损动作」三件套；大促后 7 天该批 SPU 退货率与 ODR 不超过大促前锁定阈值。

**场景 4｜把用户未满足需求变成可立项的产品机会主题**
> **验收**：每个主题附 ≥50 条原始声音、来源分布、≥5 条可点击回原文的引用；季度内至少 1 个主题进入立项评审并留下结论（立项或否决及理由）。

**场景 5｜从 Reddit 与独立站长文里挖内容话题与反对意见**
> **验收**：每双周 ≥10 个选题进内容池，≥3 个被排期采纳；brief 中每条引用 100% 可回溯到原帖 URL，且不含超出守衡 claim 边界的表述。

**能力图谱**（16 项，节选关键）

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 多源用户声音接入与增量监听 | 四渠道各看各的，没有品牌级 objection 榜 |
| 感知 | 评论树与说话人身份还原 | 分不清是买家、竞品水军还是达人粉丝 |
| 理解 | 评论到 SPU/变体的绑定与消歧 | 只能说「差评多了」，说不到哪个变体 |
| 理解 | 卖点承诺比对 | 定位不到 listing 里哪句承诺失准 |
| 理解 | VOC 四字段打标 | 标签体系不统一，无法跨月比较 |
| 理解 | 样本代表性与偏差标注 | 用小样本下大结论，整改打偏 |
| 理解 | 风险指数计算与平台门槛对齐 | 指数涨了不知会不会掉资格 |
| 推理决策 | 主题诊断与根因定位 | 停在词云与情感正负 |
| 推理决策 | 机会主题排序 | 需求散落，从未结构化 |
| 推理决策 | 改进路由决策 | 知道问题但不知道该谁改 |
| 生成 | 结构化 VOC 报告与 objection 榜 | 无统一交付物，业务方不知信谁 |
| 生成 | 卖点与 FAQ 改写建议 | 只给诊断不给改法，改不动 |
| 执行 | 跨 Agent 工单派发与回流追踪 | 整改项挂空，问题反复 |
| 评估 | 闭环效果验证 | 无法证明整改有效，下次重复投入 |
| 协同 | 舆情三方互斥判定 | 三条告警进三个群 |
| 记忆 | objection/FAQ 与卖点版本记忆 | 同一问题换个渠道再犯 |

**边界**

- **三方切分线（必须写进 OGSM）**：
  - **Signal 回答「多少」**：曝光、搜索热度、讨论量的异动与归因，服务增长与投放
  - **Vicky 回答「谁在公开说、会不会变成危机」**：媒体、KOL、监管与召回的公开事件，产出对外口径与工单闭环
  - **Echo 回答「说了什么、指向哪个 SKU 与哪句卖点、该怎么改」**：服务产品与运营
  - 同一批 Reddit 帖，Vicky 判是否形成公开危机，Echo 判是否暴露产品缺陷与 FAQ 缺口，共用 Source 采集但不共用判定规则。
- 不建任何采集器（Source 是唯一采集底座）；不做声量数量与势头告警（Signal）；不做公开舆情对外应对（Vicky）；不做品类规模/集中度/价格带/竞品份额（Market）。

> **诚实结论**：Echo 是这一簇**唯一应当存在的首选入口**。若 Market 要独立存活，Echo 的「产品机会线-品类洞察报告」必须整体迁出，否则两条产线必然重复造报告。

#### 2.7 Market｜市场洞察 Agent & 工作台（mkt.luteos.com）

> 附件里这条产线除网址外完全空白。

**定位（若保留）**：品类机会、价格带、竞品动作与市场进入判断。回答「这个类目值不值得进」。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 品类机会靠翻榜单和拍脑袋，进了卖得动但不赚钱的品 | 选品类目踩空，一年白干 |
| 2 | 没有价格带地图，定价靠「比竞品低 10%」或跟着打折 | 毛利被自己打穿 |
| 3 | 竞品动作只被「看到」，没有被判断「要不要跟」 | 被动跟随，永远慢半拍 |
| 4 | 新市场/新平台进入判断靠招商话术，合规与履约成本没人系统盘 | 进入后才发现合规办不下来 |
| 5 | 品类洞察报告给谁看、看完做什么没人定义，最后变成季度读物 | 报告产出无决策消费，等于零 |
| 6 | Market 与 Echo 的产品机会线都在出品类机会报告，口径不同 | 业务方不知信谁 |

**业务场景链路**

**场景 1｜判断一个细分品类是否值得进入**
> **验收**：每张机会卡必须带数据来源、样本量与时间窗，且包含「不进入的代价」；季度内至少 1 个明确结论（进入/不进入/换切角）在 2 周内进入立项或否决记录。**只写「建议继续观察」视为未交付。**

**场景 2｜每周竞品动作响应：跟、不跟、还是差异化**
> **验收**：每周竞品集合覆盖率 100%；每个高影响动作 48 小时内给出「跟/不跟/差异化」三选一与代价测算，不响应需写理由。只罗列信息的周报视为未交付。

**场景 3｜大促前的价格带校准与促销深度决策**
> **验收**：每个参与促销的 SKU 有大促前锁定的保本线与回升价路径；大促后 14 天价格恢复率 ≥80%，单量断崖不超过预设阈值，超阈值必须产出复盘。

**场景 4｜新市场与新平台进入判断**
> **验收**：每个判断必须同时给出合规差异清单（缺一项即判不可进）、履约成本对 CAC 上限的影响、最小验证方案与止损阈值。**不接受「先试试看」作为方案。**

**场景 5｜把市场机会翻译成产品定义输入包**
> **验收**：输入包 2 周内被产品开发评审；每个卖点假设同时具备竞品证据与用户证据（后者引用 Echo 数据，Market 不自行采评论）；季度内 ≥1 条假设进入打样。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 品类与竞品事实接入 | 翻榜单拍脑袋，进了不赚钱的品 |
| 感知 | 价格与促销快照采集 | 没有价格带地图，被自己打穿毛利 |
| 理解 | 品类边界与竞品集合构建 | 竞品集合随意，结论不可比 |
| 理解 | 价格带分层与价格-销量分布建模 | 定价靠「比竞品低 10%」 |
| 理解 | 需求信号抽取 | 把平台热搜当需求 |
| 理解 | 竞品动作识别与性质判定 | 只看到动作，不判断要不要跟 |
| 理解 | 类目合规与资格门槛核对 | 进入后才发现合规办不下来 |
| 推理决策 | 品类机会评分 / 进入退出判断 | 结论含糊，永远「继续观察」 |
| 推理决策 | 竞品响应优先级与代价测算 | 被动跟随 |
| 生成 | 品类机会卡与价格带地图 | 无交付物可评审 |
| 生成 | 新品定义输入包 | 产品开发拿不到市场输入 |
| 执行 | 洞察到决策的派发 | 报告无人消费 |
| 评估 | 机会判断事后校验 | 判断准确性无法验证 |
| 协同 | 与 Echo 的声音/市场事实分工仲裁 | 两份报告打架 |
| 记忆 | 品类事实库与判断台账 | 每次从零研究同一类目 |

**边界与诚实结论**

> **Market 当前不具备独立存在的充分理由。** 附件里它的流水线是空的，而 Echo 的「产品机会线-自动化品类洞察报告」做的正是品类机会报告；G2 的定义本身也写着「VOC 专家 + 市场洞察专家 融合」。
>
> **若保留独立，必须同时满足三条**：
> ① Echo 的品类洞察报告整体迁到 Market，Echo 只保留「未满足需求主题 + 原话证据」；
> ② Market 拥有独立的品类/竞品/价格带事实库与采集口径，且 Source 补齐 Amazon BSR、价格与上新监控（当前 Source 只覆盖 TikTok/Reddit/YouTube/Instagram/Facebook/Google Trends，**这是硬缺口**）；
> ③ Market 的产出被至少一个明确决策消费：季度品类进入/退出、新品定价、竞品响应。
>
> 三条缺一条，就应并入 Echo，作为一个「市场事实层」而不是第十五个工作台。

#### 2.8 Source｜数据采集 Agent & 工作台（scrapy.luteos.com）

**定位**：数据底座。只负责「拿得到、拿得全、拿得合规」，不做任何分析结论。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 采集没有书面授权边界，一次投诉就能掐断整条数据链 | 全公司断流 |
| 2 | UGC 里的个人信息没有脱敏标准 | 数据资产变负债 |
| 3 | 采集质量无人验收，下游的异动判断建立在浮沙上 | Signal/Echo 的结论全部不可信 |
| 4 | 采集能力重复建设，六个下游各接一套，维护成本随平台改版线性上升 | 至少 5 处重复（见 3.1） |
| 5 | 原始数据没有业务实体，下游各做一遍对齐且结论互相打架 | 同一品牌在不同报表里是三个实体 |
| 6 | 没有 SLA 和成本归因，危机时掉链子、平时说不清花了多少钱 | 断流时下游才发现，且无人负责 |

**业务场景链路**

**场景 1｜新市场开站前做采集合规预检**
> **验收**：计划数据源 100% 有「允许/受限/禁止」结论与责任人；抽样 200 条中 0 条越过清单允许范围；PII 字段 100% 按规则脱敏或丢弃；法务 5 个工作日内签字；清单可直接作为下游 Agent 的数据使用边界。

**场景 2｜采集质量月度验收并向下游交底**
> **验收**：五项指标全部有数且与上月可比；黄金集准确率 ≥90%、召回 ≥80%；T1 源 P95 延迟 ≤2 小时；任一不达标项有根因与 owner；三个下游书面确认已按新口径调整。

**场景 3｜把新竞品纳入监控并完成实体对齐**
> **验收**：50 条抽检误召回 ≤5%；90 天历史回溯成功率 ≥80%；下游至少 3 个 Agent 已切到统一实体 ID；两周后该实体噪音率 ≤10%。

**场景 4｜平台反爬升级导致断流后的应急恢复**
> **验收**：断流 2 小时内下游收到缺口声明；24 小时内恢复或给出可执行的替代方案；回补数据完整率 ≥95%；事件关闭后 5 个工作日内预案更新并演练一次。

**场景 5｜新数据源从需求到 SLA 上线**
> **验收**：契约包含 schema、SLA、缺失语义、变更通知四项且无遗漏；下游能在试采样本上跑通自己的完整分析链路；上线后两周内 0 起字段歧义工单。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 源发现与准入判定 | 无授权边界，一次投诉断链 |
| 感知 | 多通道采集执行 / 调度与限速 | 各下游自建 5 套，维护成本线性上升 |
| 理解 | 实体对齐与消歧 | 同一品牌在不同报表里是三个实体 |
| 理解 | 跨源去重与同源合并 | 一次事件被算成三次声量异动 |
| 理解 | 语种识别与归一 | 多市场数据无法合并 |
| 理解 | PII 识别与脱敏 | 数据资产变负债 |
| 理解 | 付费/自然内容标记抽取 | Signal 无法分离付费与自然声量 |
| 推理决策 | 采集优先级与成本排序 | 说不清花了多少钱 |
| 推理决策 | 源健康度诊断 | 断流时下游才发现 |
| 生成 | 统一表结构与数据契约输出 | 下游各做一遍对齐 |
| 执行 | 断流降级与备用通道切换 | 危机时掉链子 |
| 执行 | 下游缺口与变更通知 | 下游拿到坏数据不知道 |
| 评估 | 采集质量验收与黄金集抽检 | 异动判断建立在浮沙上 |
| 协同 | 订阅与 SLA 管理 | 无责任人 |
| 记忆 | 源档案与规则变更历史 | 平台改版后重复踩同一个坑 |

**边界与诚实结论**

> Source 不该是「Agent & 工作台」形态，而应是内部数据平台（data platform as product），工作台只保留源管理、质量验收、事件处置三个界面。
>
> **硬约束**：不得再出现第七套采集器。Emily/Vicky/Echo/GEO/Radar/Signal 现有的自建采集逻辑必须在两个季度内下线迁到 Source。
>
> **硬缺口**：当前 Source 只覆盖 TikTok/Reddit/YouTube/Instagram/Facebook/Google Trends，**缺 Amazon BSR、价格与上新监控**——而这正是 Market 与 Amazon 站内运营的基础。

#### 2.9 Signal｜品牌声量 Agent & 工作台（signal.luteos.com）

**定位**：只做「量」和「异动」，不做「质」的深挖。回答「变了没有、变成什么结构、严不严重、该谁处理」。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 声量涨了但没人能证明生意涨了，声量投入在预算会上说不清 | 声量预算年年被质疑 |
| 2 | 异动发现太晚，且发现后不知道该怪谁 | 预算加错人 |
| 3 | 告警要么泛滥要么没有，阈值全靠拍脑袋 | 告警疲劳，真事件被忽略 |
| 4 | 归因靠相关性巧合 | 把季节性当成功，把钱加在错的地方 |
| 5 | 声量与交易两套口径，拼不成一条链 | 无法向 CFO 交付 |
| 6 | 告警之后没有标准处置动作，同一事件在三个 Agent 各建一遍单 | 三套工单，无人真正负责 |

**业务场景链路**

**场景 1｜竞品异动的 24 小时响应**
> **验收**：异动后 24 小时内产出归因假设与证据链；假设被处置方采纳率 ≥60%；7 日复测能明确判定威胁成立或不成立；事件单 100% 有责任人与关闭时间。

**场景 2｜品牌负面声量的前哨发现与升级**
> **验收**：P0 事件 60 分钟内触达三个责任人；72 小时内产出关闭或升级结论并附证据；关闭时必须有回落数据而非「感觉没事了」；竞品黑稿与真实产品问题的分类准确率 ≥85%。

**场景 3｜达人投入的声量到成交验证**
> **验收**：每条结论必须带对照组与滞后窗口；能给出「每 1 万次有效声量带来多少品牌词搜索增量」的**区间估计而非单点**；结论被采纳进下一轮达人预算；两轮后预测偏差可量化。

**场景 4｜大促与上新期间的声量作战室**
> **验收**：连续 14 天每天 9:00 前出报，准时率 100%；三条警戒线各至少被触发并记录处置；复盘能把贡献拆成自然、付费、PR 三部分且合计可对账。

**场景 5｜品牌心智季度体检**
> **验收**：三项指标有明确公式、数据源与责任人且与上季可比；能给出加或减声量投入的明确结论而非「继续观察」；报告进入 OGSM 季度复盘并有决议记录。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 品牌与竞品声量监听 | 异动发现太晚 |
| 理解 | 声量归一化与可比口径 | 三套口径，跨月不可比 |
| 理解 | 异动构成拆解 | 知道变了，不知变成什么结构 |
| 理解 | 情感与主题归类 | 只报总量不看构成 |
| 理解 | 严重度与风险分级 | 阈值拍脑袋，告警泛滥或没有 |
| 理解 | 付费/自然声量分离 | 把买来的量当自然增长 |
| 推理决策 | 异动归因假设与证据包 | 不知该怪谁，预算加错人 |
| 推理决策 | 因果区分与对照检验 | 归因靠相关性巧合 |
| 推理决策 | 处置路由与优先级排序 | 告警后无人认领 |
| 生成 | 声量日报/周报 | 无法日常使用 |
| 生成 | 声量到交易的转译报告 | 说不清生意涨没涨 |
| 执行 | 分级告警与升级推送 | 真事件被淹没 |
| 执行 | 事件单与闭环跟踪 | 同一事件三套单 |
| 评估 | 处置后复测与效果验证 | 关闭靠「感觉没事了」 |
| 协同 | 跨 Agent 事件交接 | 三套告警三个群 |
| 记忆 | 声量基线与历史事件库 | 同类事件反复发生 |

**边界与诚实结论**

- **必须删掉附件里的「多源采集」四个字**，改为「订阅 Source」，否则它就是第七套采集器。
- 不做 VOC 语义深挖（Echo）、不做媒体外联与记者沟通（Vicky，Signal 只升级事件并交证据包）、不做内容生成与投放、不做品类前瞻（Market）。
- **与 Vicky 切分**：Signal 是前哨与分诊台，Vicky 是处置台，共享同一事件单 ID。
- **与 Echo 切分**：Echo 回答「用户在说什么」，Signal 回答「变化多大、由谁引起、该谁处理」。

> **诚实结论**：它独立成立的前提是「归因 + 分诊 + 闭环」三件事真的跑起来；否则它与 Echo、Vicky 的重叠度约 60%，合并方案是 Signal 并入 Echo 组成「声量与 VOC」一条线、Vicky 保留 PR 处置。
>
> **缺口**：当前的「因果区分与对照检验」能力没有 owner——这属于实验设计与增量测量，14 条产线里没人负责。这是必须新增的横向能力。

#### 2.10 守衡｜内容治理 Agent & 工作台（ca.luteos.com）

**定位**：整条链上**唯一「有权说不」的位置**。判的不是外部世界发生了什么，而是「我们发出去的东西、我们得出的结论站不站得住」。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 达人素材进付费加热前，授权覆盖范围核不清，混剪与二次剪辑素材实际属于无授权投放 | 素材被拒、账号处罚，最坏情况广告账户权限收紧 |
| 2 | 团队把课程讲师宣称的数字当成投放基准，写进预算公式和复盘结论 | 用别人的数据做自己的决策 |
| 3 | 经营结论的归因口径不统一，同一件事在两份报告里结论相反 | 靠谁嗓门大 |
| 4 | 规则缺失被当成「没有风险」，Agent 在无权威源的情况下照样给建议 | **最危险的一条**：库内没写禁止 ≠ 允许 |
| 5 | 判定不可追责：谁签的字、依据哪版规则、模型漏检了谁负责，全部不可回溯 | 同类错误反复犯 |

**业务场景链路**

**场景 1｜达人素材投前放行**（事件驱动，每条素材进加热池前）
1. 拉素材包、达人合作记录、平台授权凭证（TTAM / Spark Ads Video code / ACA / 红人联盟授权状态）
2. 判定授权覆盖四类（不合并成一个「能不能用」）：自然曝光、付费加热、二次剪辑、跨账号复用
3. 逐条抽取画面与文案中的 claim（功效、医学化、绝对化、对比、儿童出镜、他牌 logo、中文配音/BGM、静态轮播），匹配类目 overlay
4. 出三态：放行 / 条件放行（标明可播片段与禁播片段）/ 阻断（附规则 object_id 与原文出处）
5. 条件放行与阻断项退回达人 BD 重谈授权或交编导改剪
6. 放行后登记「素材-授权编号-可用账号-有效期」四元组

> **验收**：单批 20 条素材 24 小时内判定完成；阻断项 100% 附规则 object_id 与原文；放行项 100% 绑定授权编号与有效期；30 天内若发生平台拒审，100% 能回溯到具体判定、判定人与所用规则版本。
> **失败方式**：最常见的是**只审画面不审授权**——画面完全合规，但授权只覆盖自然曝光，一加热就违规。第二常见是把「库内没写禁止」当成允许，跳过 fail-closed。

**场景 2｜月度经营复盘结论复核**（月度，卡在复盘初稿提交前 48 小时）
- 把每条结论拆成「指标变化 + 因果断言 + 建议动作」三段
- 对每条因果断言回溯证据来源：官方规则 / 内部对照实验 / 内部案例 / **课程讲师宣称** / Agent 推断
- 校验口径：TACoS 是否含品牌词、GMV Max 归因 Key、attribution window、GA4 与财务口径差异
- 校验可迁移范围：单案例结论是否被写成全局打法，类目、市场、账号阶段是否越界
- 出三态：可发布 / 降级为打法假设 / 撤回，并生成待补证据清单
- 复盘 owner 补证后重审，结论与证据等级一并归档

> **验收**：进入决策的每条结论必须有 1 个可定位证据（source_refs 非空）；讲师宣称类结论 100% 降级为「打法假设」；口径不一致的结论 0 条进入预算决策。
> **失败方式**：不是判错，是**判得太晚**——复盘会已经开完、结论已经进了预算才复核。所以必须卡在初稿提交前，不是事后审计。

**场景 3｜知识对象晋级前复核**（事件驱动）
> **验收**：晋级对象 100% 有 source_refs 与 applicability_boundary；越界引用 0 例；存在冲突但未标 unresolved_with 的 0 例。

**场景 4｜判定被推翻后的偏差回灌**（事件驱动）
> **验收**：每个被推翻的判定 100% 进入负例库并有根因分类；修复后 90 天内同类误判复发率下降 ≥50%。

**场景 5｜新市场/新类目上线内容预检**（事件驱动）
> **验收**：新类目上线前 100% 完成预检；禁用 claim 在投放素材中出现 0 次；整改项 100% 有 owner 与截止日。
> **失败方式**：只查文案不查资质——认证文件根本没办，文案再干净也上不了架。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 采集素材与授权凭证 | 授权覆盖核不清，加热即违规 |
| 感知 | 监听平台处置回执 | 被拒审了不知道，也不回溯 |
| 理解 | 规则-对象映射 | 知道有规则，不知对应哪条内容 |
| 理解 | claim 抽取与风险分类 | 靠人眼逐条看，漏检不可控 |
| 理解 | 证据分层判定 | 讲师宣称与官方规则等同，结论被写进预算 |
| 理解 | 归因口径一致性校验 | 同一件事两份报告结论相反 |
| 推理决策 | 三态裁定与置信分层 | 只有放行/不放行，没有条件放行 |
| 推理决策 | 冲突裁决与未决标记 | 冲突被静默合并 |
| 生成 | 整改清单与替换建议 | 只说不行，不说怎么改 |
| 生成 | 复核回执 | 判定不可追责 |
| 执行 | 阻断闸门 | 无「有权说不」的位置 |
| 执行 | 工单闭环推动 | 整改项挂空 |
| 评估 | 判定回测与负例回归 | 同类误判反复发生 |
| 协同 | 人工裁定交接 | 越权裁定 |
| 记忆 | 规则版本与判定历史 | 无法回溯用的是哪版规则 |
| 记忆 | 品牌 claim 白名单与已批准话术库 | 每次重新审同一句话 |

**边界**

- 不做内容生产（Emily/Clone/GEO）；不做舆情与事实判定（Vicky/Echo/Signal）；**不做规则的原创权威源**——规则只能来自知识库 canonical 对象与外部官方源，守衡只能发现缺口并回写 blocker，不能自行发明规则，更不能把「没查到」当成「允许」；不做最终裁定人（只有建议权，规则类裁定归合规 owner）。
- **与 Daisy 切分**：Daisy 管谁能读、谁能写、多个结论之间是否矛盾；守衡管单条内容、单条结论是否成立。
- **与 PMO 切分**：PMO 定义并追踪指标口径，守衡只校验复盘结论的引用是否正确。

> **诚实结论**：守衡必须独立存在，因为它是唯一有权说不的位置。但如果它只做「按关键词查违禁词」，应该并入 Emily 的发布前检查，不值得单独一个产线。
>
> **缺口**：产品合规（认证、进口、类目准入）不在守衡范围内，而这是 S2 段的真空。

#### 2.11 Daisy｜多智能体 Agent & 工作台（mas.luteos.com）

**定位**：不是「统一入口」这个叙事，而是**强制候选区与 canonical 分离 + 权限统一台账 + 重复建设收敛**。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 同一能力被多个 Agent 重复实现，同一议题在不同工作台得出不同结论 | 约 45 处重复建设 |
| 2 | 九个入口等于九个权限孤岛，谁在读什么数据、谁能触发外部写操作没有统一台账 | 越权风险不可控 |
| 3 | 知识库被九个 Agent 并发写入，事实冲突靠「最后写入者赢」 | 品牌事实三源不一致 |
| 4 | 每个 Agent 产物格式不同，人要从 9 个地方拼一份决策材料 | 决策成本高 |
| 5 | 一次上游变更（采集器调整、平台接口变更、模型换代）会打挂多个下游，影响面靠猜 | 故障互相传染 |
| 6 | 业务方在 skills 平台自建 skill，没有权限级别、版本、回滚 | 能拼出越权动作 |

**业务场景链路**

**场景 1｜跨 Agent 结论冲突裁决**
- 检测同一 object_id 或同一 topic 在两个 Agent 输出中矛盾，生成冲突工单
- 定位双方引用的 canonical 对象与 source_refs，判断是「证据不同」还是「证据相同但解读不同」
- 按证据层级排序：官方源 > 内部对照实验 > 内部案例 > Agent 推断 > 第三方/讲师宣称
- 同层级分不出优劣时标 unresolved_with，双方结论同时保留，下游检索强制带分歧提示
- 指派领域 owner 5 个工作日内裁定，写成 supersedes 或 contradicts 关系
- 裁定回执绑定 owner 身份、对象 SHA-256、依据证据与有效期

> **验收**：冲突 100% 有 owner 与截止日；裁定后 7 天内所有下游对该议题口径一致；无法裁定的必须 5 个工作日内显式标 unresolved，**不得静默合并**。
> **失败方式**：用「多数 Agent 都这么说」或「哪个模型更强」来裁决——这两条都不是证据，必须禁止。

**场景 2｜新 Agent 接入（Clone / Market 这类空产线）**
- 先声明它要解决的业务问题、影响的 L2 指标、与现有 Agent 的差异
- 声明读域、写域、E 权限上限、是否含 PII、是否可出域
- 强制复用 Source 采集与 Daisy 适配层，**禁止自建采集**
- 用既有 golden case 跑基线，与重叠 Agent 做一致性对比
- 做「该并入还是该独立」的判断，结论写进文档
- 灰度放量，观察 2 周后再给全量入口

> **验收**：新 Agent 自建采集 0；重叠能力有明确并入计划或差异声明；上线前基线跑通且权限上限不高于 E2。
> **失败方式**：先上线再想定位，于是出现第 10 个重复造采集的产品。接入评审的第一问必须是「这个能力能不能并入现有 Agent」，答不了就不给上线。

**场景 3｜早会跨域态势**
> **验收**：单次跨域问答返回不超过 3 个 Agent 的结果且每条可溯源到 object_id 或原始数据；推断与事实必须分开标注；从提问到出简报 ≤10 分钟。
> **失败方式**：退化成把所有 Agent 的日报拼在一起。真正的价值是**跨域关联**（差评 → listing → CVR），不是汇总。

**场景 4｜知识库写入治理**
> **验收**：canonical 直写 0 次；每条 canonical 变更可回答「谁批的、依据什么证据、用的哪一版」；重复资产入库 0 次。

**场景 5｜Skill 权限治理**
> **验收**：E3+ skill 上线 100% 有审批与回滚方案；越权调用 0；异常调用 1 个工作日内熔断。
> **失败方式**：业务方为省事把一个 E3 动作拆成多个 E2 步骤绕过审批。**组合权限也必须被检查，不能只看单步。**

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | Agent 能力注册与发现 | 不知道有什么能力，重复建设 |
| 感知 | 调用与产物观测 | 重复建设不可见 |
| 理解 | 业务意图路由 | 用户不知道问哪个 Agent |
| 理解 | 产物归一化 | 人要拼 9 份材料 |
| 理解 | 冲突检测与关系生成 | 同一议题不同结论 |
| 理解 | 权限与数据边界解析 | 九个权限孤岛 |
| 推理决策 | 证据层级排序与裁决建议 | 用「多数一致」裁决 |
| 推理决策 | 任务编排与降级 | 一个环断全链断 |
| 推理决策 | 重叠度与并入判断 | 重复建设固化 |
| 生成 | 跨 Agent 决策简报 | 决策成本高 |
| 生成 | 接入适配层与 Skill 契约 | 自建采集与越权 |
| 执行 | 统一入口与多 Agent 调用 | 九个入口 |
| 执行 | 写域闸门 | 最后写入者赢 |
| 评估 | Agent 舰队评测与成本核算 | 不知哪条产线在亏钱 |
| 协同 | 人机交接与冲突升级 | 冲突无人裁 |
| 记忆 | 统一对象仓与版本 | 事实无版本，无法回溯 |

**边界**

- 不做业务判断（不回答「这个素材能不能投」「声量涨了要不要加预算」）、不做采集（归 Source）、不做裁定（裁决权在领域 owner，Daisy 只提供证据包与 unresolved 标记）、不改各 Agent 的领域逻辑（接入走适配层）。
- **与 Main 切分**：Main 管「东西怎么造、跑得贵不贵」；Daisy 管「谁在用、能不能用、冲突怎么解」。

> **诚实结论**：Daisy 有独立存在必要，但价值不在「统一入口」叙事——如果只做成一个聊天框，应并入 Main。它唯一不可替代的位置是强制候选区与 canonical 分离、权限统一台账、重复建设收敛。

#### 2.12 Main｜全栈开发 Agent & 工作台（main.luteos.com / llm.luteos.com）

**定位**：业务侧 AI 生产力交付中台（需求 → 工具 → 评测 → 成本 → 回滚）。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 模型换代只测通用 benchmark，不测业务指标，换完才发现合规漏检率上去了 | 高价值子集上更差，而这类漏检代价最高 |
| 2 | 业务需求到工具上线是周级，而跨境窗口是天级 | 旺季工具上线时促销已结束 |
| 3 | 平台规则变更传导到 Agent 执行层的链路断裂 | 知识库「知道」了，Agent 还在按旧逻辑跑 |
| 4 | AI 成本不可见，无法判断哪条产线在亏钱 | 成本失控 |
| 5 | 改了 A 挂了 B，上线靠人肉点击，没有回归与回滚 | 故障扩散 |

**业务场景链路**

**场景 1｜模型换代前的业务指标回归**
- 从各业务 Agent 收集私有评测集：守衡的 claim 负例 200 条、Emily 的脚本采用记录 300 条、Echo 的评论归类 200 条
- 定义业务指标口径：漏检率、误杀率、脚本采用率、归类准确率、单条任务成本、p95 延迟
- 新旧模型在同一批样本上跑，输出**分切片**的对比表（不能只看全局平均分）
- 出「哪个 Agent 该换、哪个不该换」的分产线结论，而非全局换型
- 灰度 10% 流量跑 2 周，观察真实业务指标
- 全量后进入月度监控

> **验收**：每次换型必须有分 Agent 的私有评测报告；换型后 30 天对应 Agent 关键业务指标下降不超过 5%；单条任务成本可查。
> **失败方式**：用全局平均分做决策。平均分高的模型可能在「美妆功效宣称」这类高价值子集上更差，必须分切片看。

**场景 2｜平台规则变更 → Agent 校验逻辑同步**
> **验收**：规则变更到 skill 上线 ≤5 个工作日；上线后 7 天内因旧规则导致的误放行为 0；每次变更可回溯到规则 object_id。
> **失败方式**：只改规则对象不改执行层。

**场景 3｜旺季作战工具的紧急上线**
> **验收**：3 天内可用；上线前有明确停止条件；上线后 0 次外部写操作；旺季结束能回答「这个工具改变了哪个决策」。
> **失败方式**：做成又一个报表。判断标准是有没有改变决策，不是有没有人打开。

**场景 4｜单位业务动作成本核算**
> **验收**：每个 Agent 有可解释的「单位业务动作成本」；降本后关键业务指标下降不超过 3%。
> **失败方式**：只看总成本不看单位成本。总成本涨可能是用得多（好事），单位成本涨才是问题。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 运行指标采集 / 规则与依赖变更监听 | 成本不可见，规则变更不知影响谁 |
| 理解 | 业务任务到技术规格的转译 | 需求翻译走样 |
| 理解 | 失败归因 | 改了 A 挂了 B 不知原因 |
| 评估 | 品牌私有评测集维护 | 只测通用 benchmark |
| 评估 | 业务指标回归判定 | 换型后漏检率上升才发现 |
| 推理决策 | 模型选型决策 | 全局换型，误伤高价值子集 |
| 推理决策 | 修复与变更优先级排序 | 修错东西 |
| 生成 | 代码 / skill / 工作流生成 | 需求周级变天级 |
| 生成 | 测试与回归集生成 | 无回归，改一处挂一片 |
| 执行 | 灰度发布与回滚 / 沙箱执行 | 故障扩散 |
| 记忆 | 组件与依赖台账 / 变更历史与决策记录 | 影响面靠猜 |
| 协同 | 需求接收与业务验收交接 | 业务方不知道能不能用 |

**边界与诚实结论**

- 不做业务判断与内容创作（生成的是工具，不是文案）；不拥有 Agent 的领域逻辑（Emily 的选题逻辑归 Emily）；**不单方面决定模型替换**——选型报告要业务 owner 签，因为风险落在业务侧（漏检率、采用率）；不做数据采集。

> **诚实结论**：附件里 Main 只填了「模型选型与评测」，这只是能力不是产线，单独做一个模型评测网站没有独立业务价值。必须重新定位为「业务侧 AI 生产力交付中台」才成立；否则应并入 Daisy 作为其工程执行层。

#### 2.13 Shopify｜ABI Shopify Agent & 工作台（shopify.luteos.com）

**定位**：唯一直接接触交易侧的产线。且必须扩为「交易与承接」入口，而不只是独立站。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | 站外已经花了钱，但没人能在 24 小时内说清 CVR 掉在哪一段（sessions→PDP→ATC→checkout→purchase），预算还在按错的归因继续加 | 预算持续投在错的环节 |
| 2 | 站点「能不能卖」没有标准，靠人肉 checklist，上线前漏一项就变成事故：GMC 拒登、checkout 缺支付、政策页缺失 | 一次事故抵掉整月营销 |
| 3 | 选品靠翻榜单看竞品，选完才发现站上演示不了、CAC 打不平、MOQ 与认证周期撑不住现金流 | 选品踩空，现金流被压死 |
| 4 | 独立站与 Amazon/TikTok Shop 没有品类与定价分工，自己打自己：站上促销把 Amazon Buy Box 打掉 | 内部互相踩 |
| 5 | 交易侧后半段（复购、订阅、邮件列表、退货归因、客服工单）没人负责，CAC 一直在买新客，LTV/CAC 算不出可放量的数 | 永远只会拉新 |
| 6 | **整份 OGSM 在交易侧是空的**：转化优化、履约库存、客服工单、复购订阅、定价促销五个环节没有一个产线认领 | 声量指标涨了但 GMV 不动时无人可问 |

**业务场景链路**

**场景 1｜放量前做站点承接体检与上线配置决策**
> **验收**：全站 blocker = 0 才允许放量；审计覆盖本期目标 LP 的 100%、Top GMV SKU 的 100%；每个 blocker 必须带 owner 与截止时间，逾期自动升级；复测 blocker 关闭率 100%；CVR、AOV、自然搜索占比三项留下**可复算基线**。

**场景 2｜CVR 掉点定位与页面迭代（诊断 → 假设 → A/B → 复测）**
> **验收**：每次诊断必须把掉点定位到单一漏斗环节并给出可证伪假设；A/B 达到统计显著（p<0.05 或贝叶斯胜率 >90%）才允许全量；单季度 ≥4 个有效测试，其中 ≥1 个带来 CVR 相对提升 ≥10% 或 AOV 提升 ≥8%；所有上线改动有回归监控。

**场景 3｜AI 选品：从「站上卖不卖得动」倒推选品（与 Market 分工）**
> **验收**：每个候选 ≥3 条独立一手信号且有可承受 CAC 上限测算；测品有明确 kill 标准（如 CAC > 上限 1.2 倍即停）；新品 90 天存活率 ≥ 目标；与 Market 结论的分歧 100% 有记录，不允许单方覆盖。

**场景 4｜渠道分工与定价带治理（独立站 vs Amazon vs TikTok Shop）**
> **验收**：任一 SKU 站上与 marketplace 到手价差 100% 落在规则带内；大促期间 0 起因价差导致的 Buy Box 丢失；每季度分工复审覆盖 100% 在售 SKU。

**场景 5｜复购与私域的最小闭环（补 OGSM 交易侧空白）**
> **验收**：90 天二购率与 LTV/CAC 有可追溯基线；邮件列表月增长 ≥2%；≥3 条自动化流上线并跑满 30 天；退货原因 100% 归入四类且至少 1 项回流为 PDP 改动；**LTV/CAC < 3 时系统自动阻断「加投放」建议**。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 站点审计采集适配器 | 「能不能卖」靠人肉 checklist，上线前漏项变事故 |
| 感知 | 交易数据口径归一 | 报表数字互相对不上 |
| 感知 | 站内搜索与行为信号抽取 | 不知道用户找不到什么 |
| 理解 | 漏斗掉点归因 | 24 小时内说不清 CVR 掉在哪一段 |
| 理解 | 商品页解释力评估 | 不知道 PDP 哪里说不清 |
| 理解 | 结构化数据与 feed 一致性校验 | GMC 拒登 |
| 理解 | 退货与差评归因 | 退货原因不回流，改错地方 |
| 推理决策 | 审计问题分级与修复排序 | 修了不重要的，blocker 还在 |
| 推理决策 | 选品候选排序与 CAC 上限测算 | 选了打不平 CAC 的品 |
| 推理决策 | SKU-渠道角色与定价带判定 | 自己打自己，Buy Box 丢失 |
| 生成 | 审计报告与分岗位工单生成 | 报告没人能执行 |
| 生成 | A/B 实验方案生成 | 拍脑袋改版，无显著性 |
| 执行 | 修复工单派发与回归监控 | 改了一处挂另一处 |
| 评估 | 复测验收与显著性判定 | 把噪声当提升 |
| 协同 | 跨产线边界路由 | 与 Market/Echo 结论打架 |
| 记忆 | 站点基线与决策版本库 | 每次改版无基线可比 |

**边界与诚实结论**

- 不做建站施工队（ABI 独立站若只是「帮你把主题装起来」，那是一次性交付项目而非 Agent 场景）；不做全类目选品穷举；不做供应链寻源与开模；不做广告投放执行与出价；不做站外内容生产；不做舆情语义分析；不改主题代码（只出工单给 Main/技术）；不做履约库存与客服工单系统本身。
- **vs Market**：Market 回答「这个类目值不值得进」；Shopify 只回答「这个品在自有站上卖不卖得动」。选品类目判断默认归 Market，Shopify 只保留「站内可验证性」否决权。

> **诚实结论**：Shopify 应**拆成三条**并扩为交易入口：① 站点承接与 CRO；② AI 选品；③ 复购与私域。
>
> **但更重要的一点**：覆盖平台里写了 Amazon US/Europe，产线里却没有任何一条对 Amazon 站内负责。这是整份 OGSM 最严重的单点空白。

#### 2.14 PMO｜OGSM 管理 Agent & 工作台（pmo.luteos.com）

**定位**：把 14 条产线的产出强制折算到 GMV / 毛利 / CAC / 复购，并据此裁决资源。

**核心问题清单**

| # | 业务问题 | 不解决的代价 |
|---|---|---|
| 1 | OGSM 的 M 全是「已完成/进行中/方案中」，没有一条经营指标，产线上线到什么程度算赢没人定义 | 无法判断投入是否值得 |
| 2 | 声量与 GMV 之间没有转译层，两边数据都对，但没人能解释为什么声量涨了生意没涨 | 声量投入被当成纯成本 |
| 3 | 指标口径不统一，复盘结论互相打架 | 会议开成辩论赛 |
| 4 | 目标拍脑袋，周动作无 owner、无系统承载 | 目标与执行脱节 |
| 5 | 产线只增不减，没有续投/收缩判断机制，「人效提升」没有基线工时无法结算 | 14 个产线永久存在，净人效可能为负 |

**业务场景链路**

**场景 1｜季度 OGSM 校准**
- 拉 L1 财务口径：GMV、毛利、CAC/MER、退货率、90 天二购率、LTV/CAC
- 拉 L2 声量中介：SOV、品牌词搜索量、品牌词 CVR、评论数与星级、NTB 占比、内容复用率
- 对每条 S 做因果贡献拆解：它假设的是「声量 → 品牌词 → GMV」的哪一段，这一段动了没有
- 判定每条 S：起效 / 未到观察窗口 / 未起效 / 反向
- 重排下季资源：砍掉未起效且无证据的，加码起效的，未到窗口的只续一次
- 每条 M 定 baseline、target、观测窗口、口径版本、owner，产线负责人签署

> **验收**：每条 M 有 baseline 与口径版本；每条 S 有可检验的因果假设；上季每条 S 有「起效/未起效/未到窗口」的明确判定；签署回执绑定 owner 身份与版本。
> **失败方式**：把校准会开成各自汇报进度。**判据是：会上有没有出现「这条策略没起效，砍掉」这样的决定。如果一次校准会没有任何策略被砍，这次会大概率是失效的。**

**场景 2｜声量异动 → GMV 传导追踪**（事件驱动 + 30/60 天回看）
> **验收**：每次异动有明确判定，**不允许「待观察」超过 8 周**；判定必须说明用了哪种因果证据（实验/准实验/相关性），**相关性结论不得直接用于预算决策**。

**场景 3｜月度经营复盘**
> **验收**：进入决策的结论 100% 有证据等级；上月假设 100% 有回看结论；三条动作都有 owner 与验收日。
> **失败方式**：复盘止于结果不止于归因。判据是：报告里有没有「我们原本以为是 X，实际是 Y」这样的句子。

**场景 4｜产线投入产出裁决**
> **验收**：每条产线有「单位业务动作成本」与「目标指标变化」；**没有基线的产线不予续投**；每条产线每 90 天必有一次裁决。

**场景 5｜跨产线资源冲突裁决**
> **验收**：裁决有量化依据；重复建设项有合并时间表；异议被记录而非被消音。

**能力图谱**

| 层 | 能力原子 | 没有它会怎样失败 |
|---|---|---|
| 感知 | 经营指标采集与对账 | 只有功能状态，没有经营数字 |
| 感知 | 目标与承诺台账 | 目标无 owner，无法追责 |
| 理解 | 指标口径解析与冲突检测 | 复盘结论互相打架 |
| 理解 | 目标-策略-动作映射 | 目标与执行脱节 |
| 理解 | 声量→GMV 传导链路建模 | 声量涨了生意没涨，无人能解释 |
| 理解 | 假设与结论的证据分级 | 讲师宣称进预算 |
| 推理决策 | 归因与贡献拆解 | 无法判断哪条策略起效 |
| 推理决策 | 目标合理性校验 | 目标拍脑袋 |
| 推理决策 | 资源分配与续投裁决 | 产线只增不减 |
| 生成 | OGSM 结构重写 | M 栏一直是功能状态 |
| 生成 | 复盘报告与决策备忘录 | 复盘无决议 |
| 执行 | 目标下发与承诺签署 | 目标无约束力 |
| 执行 | 指标偏离预警与升级 | 偏离了才发现 |

| 记忆 | 假设与决策历史库 | 同类假设反复试错 |

**边界与诚实结论**

- 不做数据采集与清洗；不做业务决策（砍产线是老板的决定，PMO 只出量化依据与选项）；不做内容与舆情判断；**不用功能进度冒充经营结果**——交付进度只能作为解释变量（为什么指标没动），不能作为 M；不做 Agent 编排（Daisy）。

> **诚实结论**：PMO 是四者中附件写得最空的（只有一个网址），但业务价值最高。如果只做任务进度跟踪，应该直接砍掉——Jira 和飞书多维表格已经能做且更好。

## 4. 结构性批判

### 4.1 G1/G2/G3 的维度选错了

问题不在分组好坏，在于**分组维度是「工具类型」而不是「业务结果」**。三个后果：

1. **G1 与 G2 在业务上无法分开。** Echo 在 G2 做 VOC，Vicky 在 G1 做舆情；Signal 在 G2 做声量异动，Emily 在 G1 做趋势洞察；Source 在 G2，却是所有产线的上游。同一条数据流被切成两个 G——这是分类维度造成的必然结果，不是执行问题。
2. **G3 拿手段冒充目标。** 守衡、Daisy、Main、Shopify、PMO 五个里没有一个是业务目标，它们是平台或职能。把职能放进 G，等于把「工具建成了」直接写成「目标达成了」——这直接导致了「完成 = 功能上线」。
3. **交易侧完全缺席。** 覆盖平台写了 Amazon US/Europe、TikTok Shop，但 14 条线里只有 Shopify 沾到交易，没有任何一条对转化、定价、库存、履约、客服、复购负责。**一个 DTC 品牌的 OGSM 里没有「卖货」，只有「喊话」。**

**替代分法（按结果 owner 切）**：

- **G1 需求**：让人找到你并相信你（Emily+Clone、Radar、Vicky-PR、GEO、Signal、Echo）
- **G2 转化**：把注意力变成订单（新建 Paid Media、Shopify 扩为交易入口、Pricing、Amazon 站内）
- **G3 留存**：让买过的人再买（新建 Retention/Subscription、CS）
- **底座下沉为支撑层，不进 G**：Source、Daisy、守衡、Main、PMO

**理由**：三个 G 与 O 的三个结果一一对应，不再有手段冒充目标；每条线有唯一的结果 owner；交易侧缺口直接暴露在 G 这一层。
**代价**：组织上 14 个 owner 重挂为 8-9 个，预算重分，两个季度指标会倒退；数据上交易侧（订单、库存、履约、工单）要新建契约，当前无 owner，需 3-6 个月。
**最小改动版**：只把 G3 从「数据资产」改成「交易与复购」，把 Daisy/Main/PMO/守衡 移出 G。代价小，但治不了 G1/G2 的重叠。

### 4.2 十四条第产线处置

| 产线 | 处置 | 理由 |
|---|---|---|
| Emily | 与 Clone 合并 | 两者的切分线在对校验里被证伪多次；合并后内部保留策略与产能两套验收，**策略侧有否决权** |
| Clone | 合并，砍掉投放场景 | 产能、谱系、授权、疲劳这四项保留 |
| Vicky | 拆成 PR 与舆情 | PR/媒体关系独立成立；舆情线并入统一事件服务 |
| GEO | 保留，砍掉内容生成，补平台内 AI | 护城河是测量闭环；漏了 Amazon Rufus 与 TikTok Shop 站内 |
| Radar | 保留，收窄范围 | 只做 IP/名人；达人供应链另建或并入其一个模块 |
| Echo | 保留，升为 VOC 主榜 owner | 砍掉与 Vicky/Signal 重复的分级 |
| Market | 砍掉，或并入 Echo | 流水线为空，没有独立价值 |
| Source | 保留，升为数据底座 | 新增主数据 ID 契约 owner |
| Signal | 保留，拆出实验设计 | 增量测量与统计显著性目前没有 owner |
| 守衡 | 保留，唯一合规裁决源 | claim 在三处打架，必须收敛到一处 |
| Daisy | 保留，移出业务 G | 品牌事实的唯一写入口，属于支撑层 |
| Main | 移出 OGSM | 它是工程职能，不是业务产线 |
| Shopify | 拆成三条，并扩为交易入口 | 覆盖平台里有 Amazon，却没有任何一条线对 Amazon 负责 |
| PMO | 保留为治理机制 | 它是治理工具，不当作产线 |

**必须新增，按优先级**：

- **P0 四条**：Paid Media（受众、预算、出价、放量、归因）、CS & After-sales（响应与工单闭环）、Retention/Subscription（复购/LTV）、Amazon 站内运营。
- **P1 四条**：Pricing/Promo、Inventory/Fulfillment、达人供应链（寄样/结佣/授权回收）、实验设计与增量测量（横向能力）。

**为什么 P0 是这四条**：补全稿里反复出现「投放操盘手」这个角色，但 14 条线里没有对应产线；Vicky 的舆情处置明确写着「交业务 owner」，可这个 owner 并不存在；14 条线全在获客前端，没有一条对 LTV 负责；覆盖平台里有 Amazon，产线里是空的。

### 4.3 「声量」作为 O 的主语不成立

三个可反驳的判断：

1. **声量是中间变量。** DTC 的终局是「以可接受的 CAC 获得可复购客户，并留下品牌资产」，声量只是一个乘数。
2. **声量可以是负资产。** 一次大规模负面同样是「声量增长」。O 写「声量有增长」而不写「净」，指标就可以被刷量作弊。
3. **三个 O 都是「有」字句**，没有基线、目标值和时间窗，无法验收。

**真实收益路径（当前 OGSM 没写）**：

```
声量（内容/PR/达人/社媒）→ 品牌词搜索（滞后 2-8 周）→ 品牌词自然流量（CVR 通常是非品牌的 2-3 倍）
  → 新客（CAC 低于付费）→ 复购 → 贡献毛利
旁路：AI 答案（GEO）→ 高意图决策场景的直接推荐
防守：口碑防线 → 降低负面事件对 CVR 的冲击 → 保护 CAC
```

**建议的正确表述**：

> 在 CAC 不升的前提下，让每一次内容/PR/达人投入，在 8 周后的「品牌词搜索量 / 品牌词 CVR / 新客 CAC」上留下可对照的变化；声量是输入，不是结果。

当前缺四件事：基线、目标值、滞后窗口、净情感口径。缺任意一项，季度评审都会退化成「发布 12 篇、曝光 300 万」。

### 4.4 人效没有度量——而且是最可能反向的指标

- 所有验收都是产出数量（脚本数、变体数、收录数、问句数、响应时间），**没有一条是「省了多少人」**。
- 更危险的是局部人效不等于全局人效：14 个 Agent 各自省 1 小时，但新增的 14 套系统在维护、对齐、数据修复上可能要花 20 小时。当前没有任何一条线算「总人力账」。
- 如果「人效」不落成指标，14 条线就会变成 14 个新增系统，**净人效大概率为负**。

**应改成这六个度量**：
1. 一条可投放素材从选题到上线的中位工时
2. 单位 GMV 的内容+运营人力成本
3. 人均管理账号/达人/SKU 数
4. 一次通过率（返工率）
5. 等待时间占比（排队/审批/跨线交接）
6. 全局账：系统维护人力 ÷ 新增系统数

### 4.5 「完成」的定义必须重构

现状是用工程状态冒充业务状态。按当前口径，14 条线全部停在 M1，最多到 M2。

| 层 | 名称 | 判定标准 | 当前覆盖 |
|---|---|---|---|
| M1 | 功能可用 | 标准输入 → 符合 schema 的输出；失败有明确错误码 | 全部 |
| M2 | 流程跑通 | 连续 4 周真实调用 ≥N 次；跨线交接字段 100% 回填；无人工兜底 | 少数 |
| M3 | 质量达标 | 抽检一致率 ≥X%；返工率 ≤Y%；拒审/误判率 ≤Z%；需人工 golden set | 几乎为零 |
| L4 | 过程改善 | 相对基线提升 + 对照/前后对照 + 归因说明 | Vicky/GEO 自认「不可直接归因」 |
| L5 | 结果改善 | 新客/CAC/复购/贡献毛利/人效，财务口径认可 | 零 |

**四条硬约束**（没有这四条，框架就是空话）：
- M1 不计入 OGSM 达成度，只有 M3 以上才算
- M2 未通过，不得宣称达到 M3
- 没有基线的产线不许立项
- 每条线必须写明「砍掉条件」——什么情况下它应该被关停

**状态到成熟度的唯一映射（可直接替换现有栏）**：

| 你现在写的 | 等价成熟度上限 |
|---|---|
| 已完成（单产线内） | M1 |
| 进行中 | M0–M1 |
| 方案中 | M0 |
| 无对应行（跨线底座） | M0，且必须显式登记为空洞 |

按此换算，14 条产线当前能到 M2 的能力约为 0——不是因为没有能力，而是因为没有一条产线写出了契约与外部消费方。

## 5. 怎么填回去

### 5.1 两栏的正确分工

**栏 A：能力图谱（Capability Registry）**

| 字段 | 说明 |
|---|---|
| capability_id | 如 P-01 / U-04 / C-02 |
| 层 | 感知 / 理解 / 推理决策 / 生成 / 执行 / 评估 / 协同 / 记忆 |
| 原子名 | 归一后的动词短语 |
| owner | 唯一产线，不是「多方共建」 |
| 契约 ID | 接口/字段/版本，如 `hook_performance.v2` |
| 消费方 | 实际接入的非 owner 产线列表（空 = M1） |
| 成熟度 | M0 / M1 / M2 / M3 |
| 最近验证 | 日期 + 验证方式（契约测试 / 生产调用量） |

**栏 B：交付进度（Work Item）**

| 字段 | 说明 |
|---|---|
| work_item_id | PM-xx 或产线任务号 |
| 所属产线 | 单值 |
| 交付物 | 具体产物，不是能力名 |
| 状态 | 已完成 / 进行中 / 方案中（保留现有语义） |
| 验收证据 | 链接：测试报告、回执、上线记录 |
| blocker | 动态解析，不写自由文本 |
| 依赖 work_item | 跨产线依赖 |

**桥接规则（最关键）**：一个 capability 对应多个 work_item；一个 work_item 也可交付多个 capability。用多对多映射表连接，**不做一对一**。成熟度**只能由消费方升级，不能由实现方自报**——至少 1 条非 owner 产线在生产环境调用并通过契约测试，才允许 M1 → M2。

### 5.2 执行顺序（不要跳步）

1. **主键字典（8 个 ID）**：event_id、claim_id、evidence_id、script_id、variant_id、ad_id、asset_id、creator_id。PMO 定标准，Daisy/Source 落库。**一次修掉 6 个交接断点。**
2. **11×14 的 RACI**：每段一个 owner、每个交接点一个字段契约 + SLA。
3. **三个 gate**：claim gate（守衡，规则未命中转人工）、授权 gate（跨线台账，无凭证不进 paid）、实验 gate（PMO，无假设编号不进测试）。当前只有 claim gate 有雏形，且默认放行。
4. **补 P0 四条产线** 或明确外包 owner。
5. **PMO 升级为「指标字典 + 实验协议」owner**：统一 ROAS/MER/CAC/LTV/复购/自然搜索占比/SOV 的口径、基线、观察窗；所有验收阈值预注册。
6. **重构 G 的分组维度**。

**没有主键和 RACI，补产线只会增加第 15、16 条孤岛。**

### 5.3 一句话回答你的困惑

> 你真正要解决的不是声量，而是「**让陌生人主动搜你、让买过的人再买、让这两件事的成本逐季下降**」。14 条产线里如果没有一条对后两件事负责，它们合起来只是在优化入口。

四个可操作推论：补上 P0 交易侧四条产线；把 G3 改成「交易与复购」；把「完成」的门槛从 M1 提到 M3；给「人效」建一本全局账。这四件事做完，再谈产线扩建。

## 6. 未核验与风险

- 本文的补全稿基于：项目 `docs/` 的 PRD 与对象 schema、`知识库/` 的 50 份 SOP 与 25 份技巧资料、`_inbox/` 93 份在途素材的文件名、以及 DTC 品牌出海行业实践。**没有验证任何产品的真实代码与线上运行状态。**
- `Clone` 与 `Market` 在附件里除网址外空白，其能力从边界反推，可信度低于其余 12 条。
- `04-平台运营技巧SOP` 中至少 7 份是课程招生页或线下课 deck，其中的数字（+329.27%、+125%、176% 等）为讲师宣称，只能作打法假设，不能作合规依据或投放基准。
- `03-平台规则SOP` 仅 2 份且全属亚马逊，TikTok Shop 与独立站的规则类文件为零；评论政策、知识产权/侵权、达人广告披露（FTC/ASA）三块在库内完全没有独立文件，必须补外部权威源。
- 指标口径以美区 DTC 常见口径为基线，EU/Amazon 站内需按市场重校准；平台 ROAS 与 MER 不可混用。
- **风险**：如果把「合并 Emily+Clone」直接当组织决策执行，策略侧会被产能 KPI 挤压，必须保留策略侧的否决权。本文只回答「链路哪里断、能力缺什么」，不回答「谁该被合并/裁撤」——组织调整必须另做能力与人力盘点。
