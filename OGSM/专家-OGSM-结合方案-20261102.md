# 专家 × OGSM 结合方案

## 0. 一句话

把 `reports/` 九份专家总结与 OGSM 的 18 项登记对齐后，得出的不是"每个专家该做什么"，而是**三条互不对齐的清单**：

| | 数量 | 具体 |
|---|---|---|
| OGSM 里点名、且已有真实建设证据 | **6** | Emily、Vicky、Shopify、Source、Echo、守衡、PMO |
| OGSM 里点名、但零建设证据 | **8** | GEO、Radar、Signal、Daisy（有名字无建设）+ Paid Media、CS、Retention、Amazon 站内（P0 零证据） |
| 有建设证据、但 OGSM 里没有位置 | **3** | Clone（有实无名）、Know（游离）、Sage（游离） |
| 已判砍/移出 | 2 | Main（移出）、Market（观察期） |

**这个读数本身就是结论**：OGSM 的四条 P0 一条报告都没有，而报告里已经建成的两条能力（any2skills 知识生产、Sage 跨境专家台）在 OGSM 里挂不上号。资源流向与战略承诺是反的。

## 1. 逐专家结合方案

### 1.1 有实有名｜六项：只补结算，不动结构

这六项的处置原则统一：**结构不动，只把"自报的进度"换成"可结算的成熟度"**。报告提供的是建设证据，不是 M2/M3 的授予权——按 OGSM 的规则，成熟度只能由消费方升级。

### 1.2 有实无名｜一项：Clone 其实已经建成了

| 项 | 内容 |
|---|---|
| OGSM 原判 | "与 Emily 合并、砍掉投放场景"，被当作一条待整合的空线 |
| 报告证据 | Main 报告的 **Recipe Agent 就是 Clone 的本体**：输入一条 TikTok 爆款视频 → 产出可克隆的 Recipe（hook / 节拍 / 口播 / 字幕公式 / 音频方向），重新绑定品牌；14 案例 eval harness + 15 条确定性规则 + rubric judge、264 单元/集成测试全通过、4 个真实模型行为失败已修复、eval 基线 13/14 |

| 结合动作 | ① **把 Recipe Agent 从 Main 移出，归入 Clone（内容产线产能域）**；② `variant_id` / `asset_id(content_*)` 的对象级 A 落到 Recipe Agent 的实现上，不再是"待指派人"；③ G1-A（Emily）不得兼任产能域的对象级 A——这正是 OGSM §8 待定项 3 的答案：**不兼任，因为产能域已有独立载体**；④ Recipe 的 `Reference` 对象与 `structure_source_id` 对应，可作为 `variant_id.structure_source_id` 的现成字段 |
| 风险 | 1 个 eval 案例仍失败（`high-abstraction` 0.55 < 0.6）、全量基线重跑未完成、`current.json` 与代码不同步。这三条必须在 M2 判定前清掉 |

这两项是本次分析最重要的发现。它们都有真实交付，但**在 18 项登记、11 条战略、3 个 G 里都找不到落点**。

| 项 | 内容 |

### 1.4 有名字无建设｜四项 + P0 零证据｜四项

这八项的共同形态：OGSM 给了名字、给了段 A、给了主指标，但**没有任何建设证据**。区别在于该建还是不建。

| 项 | 类型 | 判定 | 动作 |
|---|---|---|---|
| **Paid Media** | P0 | 零证据。这是 OGSM 诊断出的最大空洞（"0 人对花出去的钱负责"） | 最高优先级立项。首批输入可从 Vicky 的付费媒体空表 + Emily 的社媒 ROI 数据来 |
| **CS & After-sales** | P0 | 零证据 | 次高。Vicky 报告显示差评/评论处置在 Vicky 侧有部分动作，可作起点 |
| **Retention** | P0 | 零证据 | 需先有 cohort 表，依赖 `order_id`（Source） |
| **Amazon 站内** | P0 | 零证据 | 依赖 Source 补 Amazon 采集源（目前 284 端点里 Amazon 侧状态未在报告单独列出） |
| **GEO** | 业务线 | 零证据，但**第 9 键规格已于 2026-11-02 定稿** | 30 天内落库 `ai_answer_snapshot_id` 并产出 Top N 未提及问句清单，否则回退为 work_item |
| **Radar** | 业务线 | 零证据，但 `creator_id` 已在 OGSM 定义 | 达人台账未在任一报告出现——需确认是否存在于未提交的仓 |
| **Signal** | 业务线 | 零证据 | `event_id` 的主要消费者是 Echo 与 Vicky，两者都已建，Signal 本身的缺失是断链点 |
| **Daisy** | 支撑层 | 零证据，但 `claim_id`/`evidence_id` 是守衡 Claim Gate 的输入 | 守衡已建 26 条规则但没有 claim 库，这是 Claim Gate 无法生效的直接原因 |

**一个反直觉读数**：P0 四条线零证据，而 Know/Sage 两条已建成。如果按"已完成条目数"分配资源，会得出错误的优先级——这正是 OGSM §0 第二条硬规则要防的。

## 2. 三处需要立刻修正的判断

### 2.1 "规则库覆盖接近 0"是错的

| 来源 | 实际规则数 |
|---|---|
| 守衡 | 26 条生效（词典 36 / 控制点 24 / 路由 24 冻结投影） |
| Shopify | 84 条（FDA/FTC/CPSC/EPA 母婴类目） |
| 合计 | **≥110 条**，分散在两个库、两套编码 |

OGSM 原判断（"TikTok Shop 与独立站规则类文件为 0"）说的是**类目覆盖**为 0，不是**规则总数**为 0。两者必须分开：

- **规则总数**：有 110 条，够起步
- **类目覆盖**：美妆（cosmetic/medical claim）、户外（performance claim）、TikTok Shop 授权四类凭证 —— 仍然接近 0

**动作**：Claim Gate 的覆盖率门槛按类目算（正确），但"规则库为空"的说法要改，否则会误导为"从零建规则"，而实际工作是**统一 `rule_id` 并把 84 条 Shopify 规则并入守衡**。

### 2.2 B-08 三键的落地顺序需要改

原方案：`claim_id` → `variant_id` → `event_id`（选三个"都有活着的 owner"的键）。

但三份报告独立撞上同一面墙：

| 报告 | 原话 |
|---|---|
| Vicky | Tracker 品线覆盖 **0.0%**（347 条全空） |
| Echo | 产品身份解析覆盖率 **2/56** |
| Shopify | 目标准入需 SKU 主数据（Listing 依赖商品主数据） |

→ **三个专家各自用手工方法补同一件事：没有 `sku_id`。** 这比 `claim_id` 更紧急，因为它卡住三条线且造成重复建设。

**建议改序**：`order_id + sku_id` 与 `claim_id + variant_id + event_id` 并行，前者由 Source 落库（它已经是 B-08 落库方），后者维持原序。理由是前者是"止损"，后者是"建新"。

### 2.3 84 条合规规则是所有权的错位

Shopify 报告里 84 条 FDA/FTC/CPSC/EPA 规则藏在 `src/mas/rules.json`，是 Shopify 私有资产。但它判的是**品牌对外宣称合规**，与守衡的 Claim Gate 是同一件事。

**动作**：上收为守衡的 `rule_object`，Shopify 作为消费方只读。这与 OGSM「守衡是唯一合规裁决源」一致，也解掉"claim 三源"的老问题。

## 3. 落到产品（ogsm-web）

本次新增一个视图 `/experts`，数据模型：

| 字段 | 说明 |
|---|---|
| `expert` | 专家名 |
| `ogsm_line` | 映射到的 OGSM 产线；空 = 游离 |
| `evidence` | 报告文件名（可追溯） |
| `key_reading` | 报告里的关键读数 |
| `maturity_claimed` | 报告自报的成熟度 |
| `maturity_granted` | OGSM 授予的成熟度（默认不高于 M1，除非有消费方证据） |
| `gap` | 报告自指或分析识别的缺口 |
| `action` | 结合动作 |
| `status` | `aligned` / `has_real_no_name` / `name_no_build` / `orphan` / `excluded` |

新增两条校验：

| 编号 | 断言 | 抓什么 |
|---|---|---|
| **C9** | 每个业务产线必须有可追溯的建设载体（报告或 work_item） | OGSM 里有线没建设（当前 8 项） |
| **C10** | 每个专家必须映射到一条 OGSM 线，否则必须在范围排除声明里点名 | 有建设没进 OGSM（当前 Know、Sage） |

C9 与 C10 是**双向**的：一个抓"承诺了没做"，一个抓"做了没承诺"。这类双向校验比单向更有效——单向只能发现遗漏，双向能发现资源与战略的错配。
